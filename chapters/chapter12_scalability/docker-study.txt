  ㅇ Docker architecture
    - 도커는 client-server architecture 사용. 

    도커 클라이언트 -----> 도커 데몬 ---> images, container 
                                  ---> Registry(docekr hub)

  ㅇDocker Daemon
    - 도커데몬(dockerd)은 도커 client로 부터 Docker Api request를 받고(docker run, docker build 등), 도커데몬이 해당 명령어들 수행함. 
    - 데몬끼리 Communicate 가능. 
    
  ㅇ DOcker Registry
    - docker images 저장함. 
    - docker hub는 public registry이며, docker pull/push등으로 이미지를 받고, 업로드도 가능하다. 
    - centralized location for storing and sharing your container images. It can be either public or private.

  ㅇ Docker Object: 
    1. images
        - read only template이며, docker container을 creating하는 instruction임. 
        - onw image build : dockerfile로 define steps 후 create image and run it. 
                            각 instruction은 layer을 만듦. 
                            Dockerfile 수정하고, image rebuild할 경우, 변경된 layer만 rebuild됨.  -> 이미지를 lightweight, small, fast하게 가능! (기존 hyperbased VM보다)
        - 즉 도커 이미지는 하나의 거대한 파일이 아닌, 여러 개의 얇은 읽기 전용 레이어가 겹쳐진 형태임! 

    2. containers
        - 이미지를 실행한 인스턴스(프로세스) 
        - Docker API, CLI로 컨트롤가능(생성, 중지, 삭제 등) 
        - 이미지 레이어는 전부 읽기 전용인데, 프로그램이 실행되는 동안 필연적으로 파일 수정이 일어남(웹서버의 경우, 접속 로그를 파일에 기록해야하고 / db의 경우엔 데이터를 파일에 써야함.)        
          docker image 기반으로 컨테이너 생성 시 읽기 전용 이미지 레이어 위에, 읽고 쓸수있는 컨테이너 레이어를 추가헤야함! 
          실행 중 변경사항들은 모두 이 컨테이너 레이어에 저장됨. 
          컨테이너 삭제되면(docker rm) 해당 데이터들도 사라짐. -> 영구 저장 시엔 docker volumn이란 별도 저장공간을 연결하여 저장함.

  ㅇ Docker Networking. 
    - 컨테이너는 격리된 공간이지만, 외부와 통신이 가능해야함. 


  ㅇ Docker compose
    - 웹 어플리케이션 개발 시 여러 서비스 필요함(웹서버 nodejs, 데이터베이스 PostgreSql, 캐시서버 redis 등)
    - 각각을 개별 컨테이너로 실행한다면 ( docker run my-app, docker run db, docker run redis) 해줘야함. 
      매우 번거롭고, 컨테이너끼리 서로 통신하도록 네트워크까지 수동설정해줘야해서 번거로움. 
    - docker-compose.yml 파일 내에 YAML 형식으로 어플리케이션에서 사용할 모든 서비스(컨테이너), 볼륨, 네트워크 정보를 선언해둠. 
    예시: 
    version: '3.8' # 파일 규격 버전

    services: # 여기에 실행하려는 컨테이너들을 정의합니다.
    
    web: # 'web'이라는 이름의 서비스 (컨테이너)
        build: . # 현재 디렉토리의 Dockerfile을 사용해 이미지를 빌드
        ports:
        - "8080:3000" # 내 컴퓨터의 8080 포트를 컨테이너의 3000 포트와 연결
        volumes:
        - .:/app # 내 컴퓨터의 현재 폴더를 컨테이너의 /app 폴더에 연결
        depends_on: # 'db' 서비스가 먼저 실행된 후에 실행되도록 설정
        - db

    db: # 'db'라는 이름의 서비스 (컨테이너)
        image: postgres:15-alpine # PostgreSQL 공식 이미지를 사용
        volumes:
        - db-data:/var/lib/postgresql/data # 데이터 영구 저장을 위해 볼륨 연결
        environment: # 데이터베이스에 필요한 환경 변수 설정
        - POSTGRES_USER=user
        - POSTGRES_PASSWORD=password
        - POSTGRES_DB=mydb

    volumes: # 위에서 사용한 볼륨을 정의합니다.
    db-data:


    - docker-compose up으로 yml에서 정의된 모든 컨테이너 한번에 생성하고 실행함. 
      docker-compose down으로 한번에 중지하고 삭제함. 


ㅇ Docker Compose 심층 분석: '지휘'의 과정

    - docker-compose.yml은 "애플리케이션 시스템 조립 설명서"와 같음.
    - 'docker-compose up' 명령어 하나로 이 설명서에 정의된 모든 것을 자동으로 조립하고 실행함.

    - 'docker-compose up' 실행 시 내부 동작 흐름:
        1. yml 파일 분석 (Parsing):
            - 문법을 확인하고 실행할 서비스(web, db 등), 볼륨, 네트워크 등을 파악.
        2. 가상 네트워크 생성 (The Magic!):
            - 가장 중요한 단계. 이 프로젝트만을 위한 격리된 가상 네트워크를 자동으로 생성함. (예: <폴더명>_default)
            - 이 네트워크 덕분에 컨테이너들은 설정 없이도 '서비스 이름'으로 서로 통신 가능.
        3. 볼륨 생성:
            - yml 파일에 정의된 볼륨(데이터 영구 저장을 위함)이 없으면 새로 생성.
        4. 이미지 준비 (Build / Pull):
            - 'build: .' 가 명시된 서비스는 Dockerfile을 이용해 이미지를 빌드.
            - 'image: ...' 가 명시된 서비스는 로컬에 이미지가 없으면 Docker Hub에서 다운로드(pull).
        5. 컨테이너 생성 및 실행:
            - 준비된 이미지를 바탕으로 실제 컨테이너를 생성하고 실행함.
            - depends_on 옵션에 따라 서비스 실행 순서를 보장함. (예: DB가 먼저 실행된 후 웹서버 실행)
            - ports, volumes, environment 등의 설정을 컨테이너에 적용.
        6. 로그 스트리밍:
            - 실행된 모든 컨테이너의 로그를 하나의 터미널에 모아서 실시간으로 보여줌. 어떤 컨테이너의 로그인지 구분하기 쉽게 서비스 이름이 붙어서 나옴.

    - 'docker-compose down' 실행 시:
        - 'up'의 역순으로 정리 작업을 수행.
        - 컨테이너 중지 및 삭제, 네트워크 삭제.
        - 중요: 데이터 유실 방지를 위해 볼륨(volume)은 기본적으로 삭제하지 않음! (완전 삭제는 'down -v' 옵션 필요)


ㅇ Docker Compose 네트워크 심층 탐구: "아파트 단지 통신망"

    - 1. 기본 네트워크 (Default Network): "자동으로 설치되는 단지 전체 인터폰"
        - yml 파일에 'networks:' 설정을 전혀 하지 않아도 자동으로 생성됨.
        - 가장 중요한 특징: 서비스 이름 = 호스트 이름 (Service Discovery)
            - web 컨테이너에서 DB에 접속할 때, IP 주소 대신 서비스 이름 'db'를 사용하면 Docker가 알아서 해당 컨테이너로 연결해줌.
            - 예시 코드 (Node.js): new Client({ host: 'db', ... })
        - 대부분의 경우, 이 기본 네트워크만으로 충분함.

    - 2. 사용자 정의 네트워크 (Custom Networks): "VVIP 전용 보안 통로 만들기"
        - 왜 필요? 더 세밀한 통신 제어와 보안 강화를 위해.
        - 컨테이너 그룹을 나눠 어떤 그룹은 서로 통신하게 하고, 어떤 그룹은 못하게 격리시킴.
        - 사용 방법:
            1. yml 파일 최하단에 'networks:' 블록을 정의. (예: frontend, backend)
            2. 각 서비스 설정에 'networks:' 블록을 추가하여 어떤 네트워크에 속할지 명시.
        - 대표적인 예시: Frontend / Backend 네트워크 분리
            - proxy (Nginx): frontend 네트워크에만 속함. (외부와 유일한 통로)
            - webapp (Node.js): frontend와 backend 네트워크에 모두 속함. (다리 역할)
            - database: backend 네트워크에만 속함. (가장 안전한 내부)
            - 결과: proxy가 해킹당해도 database에는 직접 접근이 불가능한 보안 구조가 만들어짐.

ㅇ Docker 볼륨 (Volume): 데이터 영속성의 핵심

    - 문제점: 컨테이너는 '휘발성'
        - 컨테이너가 생성하는 데이터(DB, 로그 등)는 컨테이너 레이어에 저장됨.
        - 컨테이너가 삭제되면 이 데이터도 함께 사라짐.
        - 영구적으로 보존해야 하는 데이터는 컨테이너 외부에 저장해야 함.

    - 해결책: 호스트(PC) 저장소와 연결(Mount)
        - 컨테이너 외부의 호스트 저장 공간을 컨테이너 내부의 특정 폴더처럼 연결하는 기술.
        - 두 가지 주요 방식: 볼륨 (Volume) vs. 바인드 마운트 (Bind Mount)

    - 1. 볼륨 (Volumes): "Docker가 관리하는 안전한 데이터 금고" (권장 방식)
        - 개념: Docker가 직접 생성하고 관리하는 호스트 내의 특별한 저장 공간.
        - 관리 주체: Docker. (사용자는 정확한 경로를 알 필요 없음)
        - 특징:
            - Docker 명령어로 체계적인 관리 가능 (생성, 삭제, 백업).
            - 이식성이 높음. (어떤 OS, 어떤 개발자 PC에서도 동일하게 동작)
            - 성능상 이점이 있음.
            - 안전함 (호스트의 중요 파일을 실수로 연결할 위험이 없음).
        - 언제 사용?
            - 애플리케이션이 생성하고 관리하는 모든 영구 데이터.
            - 예: 데이터베이스 데이터 파일, 사용자가 업로드한 파일, 애플리케이션 로그.
        - yml 예시:
            - services:
                  db:
                      volumes:
                          - db-data:/var/lib/postgresql/data # 'db-data'라는 볼륨을 컨테이너 경로에 연결
            - volumes:
                  db-data: {} # 'db-data' 볼륨을 정의

    - 2. 바인드 마운트 (Bind Mounts): "내 PC의 폴더를 그대로 컨테이너에 연결"
        - 개념: 호스트 머신의 특정 파일이나 폴더를 컨테이너 경로에 직접 1:1로 매핑.
        - 관리 주체: 사용자. (정확한 호스트 경로를 명시해야 함)
        - 특징:
            - 실시간 동기화. (호스트에서 코드 수정 -> 컨테이너에 즉시 반영)
            - 개발자에게 직관적.
            - 이식성이 낮음. (호스트 경로에 의존하므로 환경이 바뀌면 수정 필요)
            - 권한 문제가 발생할 수 있음.
        - 언제 사용?
            - 주로 개발(Development) 환경에서 사용.
            - 예: 소스 코드 공유 (nodemon 등으로 자동 재시작), 설정 파일 주입.
        - yml 예시:
            - webapp:
                  volumes:
                      - ./src:/app/src # 호스트의 ./src 폴더를 컨테이너의 /app/src에 연결

    - 최종 정리: 언제 무엇을 써야 할까?
        - 데이터 (DB, 로그, 업로드): 볼륨 (Volume) 사용. -> Production 환경의 기본.
        - 소스 코드 & 설정 파일: 바인드 마운트 (Bind Mount) 사용. -> Development 환경의 필수.
