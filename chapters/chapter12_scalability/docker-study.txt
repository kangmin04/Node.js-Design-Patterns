 ㅇ DOCKER: 가상화 기술의 역사와 핵심 

    ## Docker의 역사: 거시적 관점

    1세대: 물리 서버와 "작동 환경 지옥" ( ~ 2000년대 초반)
        - 문제점:
            - 개발 PC, 테스트 서버, 운영 서버의 환경(OS, 라이브러리 버전)이 모두 달라 배포 시 에러 발생 빈번. "제 컴퓨터에서는 잘 되는데요?"의 시대.
            - 하나의 물리 서버에 여러 앱을 설치하면 라이브러리 버전이 충돌하는 "의존성 지옥(Dependency Hell)" 발생.

    2세대: 가상 머신(VM)의 등장과 "무거운 격리" (2000년대 초반 ~ 2010년대 초반)
        - 해결책: 가상 머신 (VMware, VirtualBox 등). 하나의 고성능 서버 위에 여러 개의 독립된 가상 컴퓨터를 생성.
        - 장점:
            - 완벽한 격리: 각 VM은 독립된 OS(Guest OS)를 가지므로 앱끼리 절대 충돌하지 않음.
        - 단점:
            - 너무 무거움: 각 VM이 OS를 통째로 포함해 이미지 용량이 수 GB에 달하고 부팅에 수 분이 걸림.
            - 자원 낭비: OS 자체를 실행하는 데 상당한 CPU, 메모리 자원 소모.

    3세대: Docker 컨테이너의 혁명과 "가벼운 격리" (2013년 ~ 현재)
        - 혁신: "OS까지 통째로 가상화할 필요 없이, 앱과 라이브러리만 격리하자!"
        - 해결책: 도커(Docker). 호스트 서버의 OS 커널은 공유하면서, 프로세스/파일 시스템만 격리.
        - 장점:
            - 매우 가벼움: OS를 포함하지 않아 이미지가 수십~수백 MB에 불과.
            - 매우 빠름: 실행(컨테이너화)에 불과 몇 초 소요.
        - 결과: "Build once, run anywhere(한 번 빌드하면, 어디서든 실행된다)"가 현실이 됨.

    4세대: 컨테이너 오케스트레이션의 시대 (2015년 ~ 현재)
        - 새로운 문제: 컨테이너가 수백, 수천 개로 늘어나자 관리가 어려워짐. (누가 죽은 컨테이너를 다시 실행시키나? 트래픽 몰리면 어떻게 확장하나?)
        - 해결책: 컨테이너 오케스트레이션 (e.g., Kubernetes). 수많은 컨테이너를 지휘자처럼 관리하는 시스템.
            - 자동 복구(Self-healing), 오토 스케일링(Auto-scaling), 서비스 디스커버리 등 제공.



  ㅇ Docker 핵심 개념

    - 이미지 (Image):
        - 애플리케이션과 실행 환경(라이브러리, 소스코드 등)을 담아놓은 읽기 전용 템플릿.
        - "설치 파일" 또는 "설계도"에 비유할 수 있음.
        - `Dockerfile`이라는 레시피 파일을 통해 만들어짐.

    - 컨테이너 (Container):
        - 이미지를 실제로 메모리에 올려 실행한 인스턴스.
        - 격리된 공간에서 실행되는 "프로세스"라고 볼 수 있음.
        - 하나의 이미지로 수많은 컨테이너를 생성할 수 있음.

    - Dockerfile:
        - 이미지를 어떻게 만들지 순서대로 기록한 텍스트 파일. (e.g., "Node.js 22 버전 기반으로, 내 코드를 복사하고, npm install을 실행한 뒤, npm start로 앱을 실행해줘.")

    ## VM vs 컨테이너: "커널 공유"의 진짜 의미

    - 운영체제(OS)의 구조:
        - 커널 공간 (Kernel Space): OS의 핵심. 하드웨어(CPU, 메모리)를 직접 제어. 일반 앱은 접근 불가. (비유: 식당의 총괄 헤드 셰프)
        - 사용자 공간 (User Space): 일반 앱(Node.js, Chrome 등)이 실행되는 영역. 하드웨어 필요 시 커널에게 요청(System Call)함. (비유: 요리사들이 요리하는 공간)

    - 가상 머신(VM) 방식: "독립된 미니 주방을 통째로 빌리는 것"
        - 각 VM은 자신만의 OS, 즉 독립된 '게스트 OS 커널'을 가짐.
        - 완벽하게 격리되지만, OS를 중복 실행하므로 무겁고 비효율적.

    - 도커 컨테이너 방식: "하나의 주방을 효율적으로 나눠 쓰는 것"
        - 모든 컨테이너가 **호스트 OS의 커널 하나를 공유**함. 별도의 게스트 OS 커널이 없음.
        - "어떻게 충돌 없이 공유하는가?" -> 커널의 두 가지 핵심 기술 사용.
            1.  **네임스페이스 (Namespaces): 가상 칸막이**
                - 커널이 각 컨테이너에게 독립된 공간에 있는 것처럼 착각하게 만듦. (e.g., A 컨테이너는 B 컨테이너의 프로세스를 볼 수 없음)
            2.  **컨트롤 그룹 (Cgroups): 자원 할당량**
                - 커널이 각 컨테이너가 사용할 수 있는 CPU, 메모리 양을 엄격하게 제한하고 할당함.

    - 결론:
        - "커널을 공유한다" = 여러 컨테이너들이 별도의 OS 없이, 단 하나의 OS 커널이 제공하는 네임스페이스와 Cgroups 기능을 통해 효율적으로 격리되어 실행된다는 의미.
        - 이 "가볍고 빠른" 특성 덕분에 chapter12에서 배운 동적인 확장(Dynamic Scaling)이 가능해짐.

    
    package.json 파일: 의존성 명세서. 
    docker이미지는 내 프로그램이 어디서든 똑같이 실행되도록 독립된 실행환경을 만드는 것. 
    즉, COPY 시 사용할 코드 및 package.json도 포함해서 WORKDIR에 넣어줘야함. 

    - 도커 파일 작성: 
    FROM node:24-slim

    # 작업 디렉터리 먼저 설정
    WORKDIR /app

    # 1. package.json 파일을 먼저 복사 (의존성이 변경될 때만 다음 단계 재실행)
    COPY package.json .

    # 2. 의존성 설치
    RUN npm install

    # 3. 나머지 모든 소스 코드 복사
    COPY . .

    # 4. 포트 노출
    EXPOSE 8080

    # 5. 컨테이너 시작 명령어
    CMD ["npm", "start"]

    - dockerfile에서 package.json 먼저 복사하는 이유? 
    : docker의 layer cache 기능 활용하고자 험. 
    비효율적인 방법: 만약 소스 코드 전체를 먼저 복사(COPY . .)하고 npm install을 실행하면, 코드 한 줄만 수정해도 Docker는 COPY 단계가 변경되었다고 인식해서 그 이후의 모든 단계, 
                   즉 시간이 오래 걸리는 npm install을 매번 다시 실행함. 
    효율적인 방법: 하지만 package.json을 먼저 복사하면, 의존성이 바뀌지 않는 한 npm install 단계는 캐시된 레이어를 그대로 재사용합니다. 
                 개발 중에 소스 코드만 계속 바꿀 때는, npm install은 건너뛰고 마지막 COPY . . 단계만 새로 실행하므로 이미지 빌드 속도가 엄청나게 빨라지는 거죠!




  ## OS 기본 개념: 터미널, 셸(Shell), 그리고 프로세스

    - 배경: Docker 컨테이너의 PID 네임스페이스 격리를 이해하기 위해, OS의 기본적인 프로세스 동작 방식을 알아야 함.

    - 프로세스(Process)란?
        - 컴퓨터에서 "실행 중인 모든 프로그램"을 의미.
        - 사용자가 실행하는 앱(Chrome, Node.js)과 시스템이 필요로 하는 백그라운드 서비스 모두가 프로세스.
        - OS는 각 프로세스를 관리하기 위해 고유 번호(PID: Process ID)를 부여.

    - 터미널의 정체: 셸(Shell) 프로세스
        - 우리가 사용하는 터미널 창은 그 자체가 하나의 프로세스임.
        - 터미널 창 내부에서는 '셸(Shell)'이라는 프로그램이 항상 실행되고 있음. (e.g., `bash`, `zsh`)
        - `ps` 명령어 결과에 `bash`가 보이는 이유: 터미널 창 안에서 `bash` 프로그램이 실행 중이기 때문.
        - 셸의 역할: 사용자로부터 명령어를 입력받아 해석하고, 다른 프로그램을 실행시켜주는 '명령어 해석기'.

    - 부모-자식 관계: 모든 명령어는 셸의 자식 프로세스
        - 1. 사용자가 터미널(셸)에 `ps`와 같은 명령어를 입력.
        - 2. 셸(부모 프로세스)은 `ps`라는 새로운 프로그램(자식 프로세스)을 생성하여 실행함.
        - 3. 자식 프로세스(`ps`)는 자신의 임무를 완수하고 즉시 종료됨.
        - 4. 부모 프로세스(셸)는 다시 사용자의 다음 입력을 대기.
        - `ps -af` 결과에서 자식 프로세스의 `PPID`(Parent Process ID)가 셸의 `PID`인 이유가 바로 이것.

    - `ps` 명령어의 미스터리: `ls`는 안 보이고, `ps`는 왜 보이는가?
        - 핵심: 명령어의 실행 순서와 `ps`의 역할 때문.
        - `ls`가 보이지 않는 이유:
            - `ls` 명령어는 실행 시간이 매우 짧아 (수 밀리초) 순식간에 종료됨.
            - 그 후에 `ps` 명령어를 실행하면, `ps`가 스냅샷을 찍는 시점에는 `ls` 프로세스는 이미 사라지고 없음.
        - `ps`가 보이는 이유 ("자기 참조"):
            - `ps` 명령어는 "자신이 실행되는 바로 그 순간"의 프로세스 목록을 가져옴.
            - 커널이 프로세스 목록을 만들 때, 요청을 한 `ps` 자신도 당연히 "실행 중인 프로세스"이므로 목록에 포함됨.
            - 비유: 출석을 부르는 조교가 자기 자신도 출석부에 포함해서 보고하는 것과 같음.

    - `ps` 와 `ps aux`의 차이
        - `ps`: 기본적으로 현재 내가 사용 중인 터미널(TTY)에 연결된 프로세스만 보여줌. (그래서 `bash`와 `ps` 자신만 보였던 것)
        - `ps aux` 또는 `ps -ef`: 현재 OS에서 실행 중인 **모든 사용자의 모든 프로세스**를 보여줌. 시스템의 전체 상황을 볼 때 사용.

    - 일반적인 프로세스의 실행 방식 
        1. 리눅스 서버는  커널 공간, 사용자 공간으로 나뉨
        2. 사용자가 node app.mjs 실행하면 node라는 프로세스가 사용자 공간에서 실행됨. 
        3. node 프로세스는, 파일 읽거나 네트워크 요청등의 작업들을 하드웨어 제어가 아닌, 커널에게 시스템 콜을 보내 요청함. 
        ( 이 node 프로세스는 서버에서 실행중인 다른 프로세스들과 통신 가능함.)

    - 컨테이너의 방식. 
        1. 컨테이너도 결국 프로세스다. (docker run으로 컨테이너 실행하면, 그 안에서 node app.mjs는 똑같은 user space에서 실행되는 하나의 node 프로세스임)
        2. 차이점: DOCKER의 핵심은 커널에게 이 프로세스를 특별하게 다뤄달라고 요청하는것.
        2-1. 커널은 컨테이너에게 네임스페이스라는 가상의 격리된 공간을 제공함. 
        (컨테이너 안에서 ps 치면 호스트의 다른 프로세스들은 안보이고 격리된 공간의 자기 자신 프로세스만 보임/ 네트워크도 본인만의 IP 가짐/ 독립된 파일 시스템 가짐)
        2-2. 커널은 컨테이너의 자원 사용량 제한 가능. 


    - docker Build: 
    docker build는 여 최종 이미지 만들어냄. 
    docker build . 실행 시 
    1. docker 클라이언트는 현재 디렉토리(와 그 안의 모든것)를 빌드 컨텍스트로 지정함
    2. 빌드 컨텍스트로 지정된 모든 파일과 하위 디렉터리를 하나의 tar 아카이브로 묶어서 Docker 데몬(실제 빌드를 수행하는 백그라운드 프로세스)에게 전송
    3. Docker 데몬은 전달받은 컨텍스트안에서 dockerfile 찾음. 
    5. Dockerfile의 명령어들을 한줄씩 실행하며 이미지 빌드함. (FROM, COPY, RUN)
    6. 모든 단계 끝나면 새로운 docker 이미지 생성됨. 

    docker build -t my-app:1.0 . 처럼 -t (tag) 옵션을 사용해 이미지에 이름:태그를 붙여주는 것이 일반적
    불필요한 파일 제외하기 (.dockerignore 파일): node_modules 폴더나 .git 폴더처럼 이미지에 포함될 필요가 없는경우 명시함. 

    - Docker Run: 
    docker run은 docker 컨테이너를 실행해달라는 기본 명령어
    docker run -it -p 8080:8080 10c2fc07b
    옵션들: 
    1. -i : --interactive(상호작용모드). 컨테이너의 STDIN을 계속 열어둬서 내 키보드 입력 받을수있게 유지함. 
    2. -t : 가상 터미널 할당. 
    3. -p (--publish): 포트 포워딩(Port Forwarding) 또는 포트 매핑(Port Mapping). 호스트(내 컴퓨터)의 포트와 컨테이너 내부의 포트를 연결해줍니다.
    -p 8080:8080 : 내 컴퓨터의 localhost:8080으로 들어오는 모든 네트워크 요청을 컨테이너 내부의 8080포트로 전달해줌. 
    이 옵션없다면 컨테이너는 가상 네트워크 내에서만 실행되서 외부에서 접속 불가!

  ㅇ Docker Networking. 
    - 컨테이너는 격리된 공간이지만, 외부와 통신이 가능해야함. 


  ㅇ Docker compose
    - 웹 어플리케이션 개발 시 여러 서비스 필요함(웹서버 nodejs, 데이터베이스 PostgreSql, 캐시서버 redis 등)
    - 각각을 개별 컨테이너로 실행한다면 ( docker run my-app, docker run db, docker run redis) 해줘야함. 
      매우 번거롭고, 컨테이너끼리 서로 통신하도록 네트워크까지 수동설정해줘야해서 번거로움. 
    - docker-compose.yml 파일 내에 YAML 형식으로 어플리케이션에서 사용할 모든 서비스(컨테이너), 볼륨, 네트워크 정보를 선언해둠. 
    예시: 
    version: '3.8' # 파일 규격 버전

    services: # 여기에 실행하려는 컨테이너들을 정의합니다.
    
    web: # 'web'이라는 이름의 서비스 (컨테이너)
        build: . # 현재 디렉토리의 Dockerfile을 사용해 이미지를 빌드
        ports:
        - "8080:3000" # 내 컴퓨터의 8080 포트를 컨테이너의 3000 포트와 연결
        volumes:
        - .:/app # 내 컴퓨터의 현재 폴더를 컨테이너의 /app 폴더에 연결
        depends_on: # 'db' 서비스가 먼저 실행된 후에 실행되도록 설정
        - db

    db: # 'db'라는 이름의 서비스 (컨테이너)
        image: postgres:15-alpine # PostgreSQL 공식 이미지를 사용
        volumes:
        - db-data:/var/lib/postgresql/data # 데이터 영구 저장을 위해 볼륨 연결
        environment: # 데이터베이스에 필요한 환경 변수 설정
        - POSTGRES_USER=user
        - POSTGRES_PASSWORD=password
        - POSTGRES_DB=mydb

    volumes: # 위에서 사용한 볼륨을 정의합니다.
    db-data:


    - docker-compose up으로 yml에서 정의된 모든 컨테이너 한번에 생성하고 실행함. 
      docker-compose down으로 한번에 중지하고 삭제함. 


ㅇ Docker Compose 심층 분석: '지휘'의 과정

    - docker-compose.yml은 "애플리케이션 시스템 조립 설명서"와 같음.
    - 'docker-compose up' 명령어 하나로 이 설명서에 정의된 모든 것을 자동으로 조립하고 실행함.

    - 'docker-compose up' 실행 시 내부 동작 흐름:
        1. yml 파일 분석 (Parsing):
            - 문법을 확인하고 실행할 서비스(web, db 등), 볼륨, 네트워크 등을 파악.
        2. 가상 네트워크 생성 (The Magic!):
            - 가장 중요한 단계. 이 프로젝트만을 위한 격리된 가상 네트워크를 자동으로 생성함. (예: <폴더명>_default)
            - 이 네트워크 덕분에 컨테이너들은 설정 없이도 '서비스 이름'으로 서로 통신 가능.
        3. 볼륨 생성:
            - yml 파일에 정의된 볼륨(데이터 영구 저장을 위함)이 없으면 새로 생성.
        4. 이미지 준비 (Build / Pull):
            - 'build: .' 가 명시된 서비스는 Dockerfile을 이용해 이미지를 빌드.
            - 'image: ...' 가 명시된 서비스는 로컬에 이미지가 없으면 Docker Hub에서 다운로드(pull).
        5. 컨테이너 생성 및 실행:
            - 준비된 이미지를 바탕으로 실제 컨테이너를 생성하고 실행함.
            - depends_on 옵션에 따라 서비스 실행 순서를 보장함. (예: DB가 먼저 실행된 후 웹서버 실행)
            - ports, volumes, environment 등의 설정을 컨테이너에 적용.
        6. 로그 스트리밍:
            - 실행된 모든 컨테이너의 로그를 하나의 터미널에 모아서 실시간으로 보여줌. 어떤 컨테이너의 로그인지 구분하기 쉽게 서비스 이름이 붙어서 나옴.

    - 'docker-compose down' 실행 시:
        - 'up'의 역순으로 정리 작업을 수행.
        - 컨테이너 중지 및 삭제, 네트워크 삭제.
        - 중요: 데이터 유실 방지를 위해 볼륨(volume)은 기본적으로 삭제하지 않음! (완전 삭제는 'down -v' 옵션 필요)


ㅇ Docker Compose 네트워크 심층 탐구: "아파트 단지 통신망"

    - 1. 기본 네트워크 (Default Network): "자동으로 설치되는 단지 전체 인터폰"
        - yml 파일에 'networks:' 설정을 전혀 하지 않아도 자동으로 생성됨.
        - 가장 중요한 특징: 서비스 이름 = 호스트 이름 (Service Discovery)
            - web 컨테이너에서 DB에 접속할 때, IP 주소 대신 서비스 이름 'db'를 사용하면 Docker가 알아서 해당 컨테이너로 연결해줌.
            - 예시 코드 (Node.js): new Client({ host: 'db', ... })
        - 대부분의 경우, 이 기본 네트워크만으로 충분함.

    - 2. 사용자 정의 네트워크 (Custom Networks): "VVIP 전용 보안 통로 만들기"
        - 왜 필요? 더 세밀한 통신 제어와 보안 강화를 위해.
        - 컨테이너 그룹을 나눠 어떤 그룹은 서로 통신하게 하고, 어떤 그룹은 못하게 격리시킴.
        - 사용 방법:
            1. yml 파일 최하단에 'networks:' 블록을 정의. (예: frontend, backend)
            2. 각 서비스 설정에 'networks:' 블록을 추가하여 어떤 네트워크에 속할지 명시.
        - 대표적인 예시: Frontend / Backend 네트워크 분리
            - proxy (Nginx): frontend 네트워크에만 속함. (외부와 유일한 통로)
            - webapp (Node.js): frontend와 backend 네트워크에 모두 속함. (다리 역할)
            - database: backend 네트워크에만 속함. (가장 안전한 내부)
            - 결과: proxy가 해킹당해도 database에는 직접 접근이 불가능한 보안 구조가 만들어짐.

ㅇ Docker 볼륨 (Volume): 데이터 영속성의 핵심

    - 문제점: 컨테이너는 '휘발성'
        - 컨테이너가 생성하는 데이터(DB, 로그 등)는 컨테이너 레이어에 저장됨.
        - 컨테이너가 삭제되면 이 데이터도 함께 사라짐.
        - 영구적으로 보존해야 하는 데이터는 컨테이너 외부에 저장해야 함.

    - 해결책: 호스트(PC) 저장소와 연결(Mount)
        - 컨테이너 외부의 호스트 저장 공간을 컨테이너 내부의 특정 폴더처럼 연결하는 기술.
        - 두 가지 주요 방식: 볼륨 (Volume) vs. 바인드 마운트 (Bind Mount)

    - 1. 볼륨 (Volumes): "Docker가 관리하는 안전한 데이터 금고" (권장 방식)
        - 개념: Docker가 직접 생성하고 관리하는 호스트 내의 특별한 저장 공간.
        - 관리 주체: Docker. (사용자는 정확한 경로를 알 필요 없음)
        - 특징:
            - Docker 명령어로 체계적인 관리 가능 (생성, 삭제, 백업).
            - 이식성이 높음. (어떤 OS, 어떤 개발자 PC에서도 동일하게 동작)
            - 성능상 이점이 있음.
            - 안전함 (호스트의 중요 파일을 실수로 연결할 위험이 없음).
        - 언제 사용?
            - 애플리케이션이 생성하고 관리하는 모든 영구 데이터.
            - 예: 데이터베이스 데이터 파일, 사용자가 업로드한 파일, 애플리케이션 로그.
        - yml 예시:
            - services:
                  db:
                      volumes:
                          - db-data:/var/lib/postgresql/data # 'db-data'라는 볼륨을 컨테이너 경로에 연결
            - volumes:
                  db-data: {} # 'db-data' 볼륨을 정의

    - 2. 바인드 마운트 (Bind Mounts): "내 PC의 폴더를 그대로 컨테이너에 연결"
        - 개념: 호스트 머신의 특정 파일이나 폴더를 컨테이너 경로에 직접 1:1로 매핑.
        - 관리 주체: 사용자. (정확한 호스트 경로를 명시해야 함)
        - 특징:
            - 실시간 동기화. (호스트에서 코드 수정 -> 컨테이너에 즉시 반영)
            - 개발자에게 직관적.
            - 이식성이 낮음. (호스트 경로에 의존하므로 환경이 바뀌면 수정 필요)
            - 권한 문제가 발생할 수 있음.
        - 언제 사용?
            - 주로 개발(Development) 환경에서 사용.
            - 예: 소스 코드 공유 (nodemon 등으로 자동 재시작), 설정 파일 주입.
        - yml 예시:
            - webapp:
                  volumes:
                      - ./src:/app/src # 호스트의 ./src 폴더를 컨테이너의 /app/src에 연결

    - 최종 정리: 언제 무엇을 써야 할까?
        - 데이터 (DB, 로그, 업로드): 볼륨 (Volume) 사용. -> Production 환경의 기본.
        - 소스 코드 & 설정 파일: 바인드 마운트 (Bind Mount) 사용. -> Development 환경의 필수.
