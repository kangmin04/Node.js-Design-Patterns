 ㅇ 쿠버네티스 
    - declarative configuration model: 
        don’t need to write instructions for every step. 
        Instead, you describe the final state you want, and Kubernetes figures out how to make it happen and keep it that way
        예시:3개의 replicas (instances)를 running이라고 선언하면,  Kubernetes will make sure that three containers are always up. If one crashes, it starts a new one automatically.
    - tools: 
        1. kubectl: lets us deploy apps, inspect resources, manage logs, and more.
        2. minikube:  create a Kubernetes cluster for local experiments. (creates a fully functional single-node Kubernetes cluster right on your laptop.)
    - 사용이유? 
        사용자들은 application이 24/7 가능하길 바라고, 개발자들은 배포를 하루에 여러번 즉각적으로, 서버 종료없이 하기를 원함. 
        Containerization helps package software to serve these goals, enabling applications to be released and updated without downtime
    - 관련 명령어 
        1. kubectl create deployment
            - 애플리케이션의 관리 주머니(Pod)와 복제본 제어(ReplicaSet)
            - 쿠버네티스에서 가장 작은 배포 단위는 Pod(팟)
            하지만 우리가 컨테이너를 하나하나 직접 띄우면, 그 컨테이너가 죽었을 때 아무도 살려주지 않음 -> 우리는 Deployment(디플로이먼트)라는 관리자를 만듦. 
            - kubectl create deployment hello-web --image=hello-web:v1
            - 쿠버네티스 내부 동작: 
                1. 쿠버네티스 마스터에게 "나는 `hello-web:v1` 이미지를 쓰는 똑똑한 관리자(Deployment)를 만들고 싶어"라고 선언. 
                2. Deployment는 뒤에서 몰래 ReplicaSet(레플리카셋)이라는 복제본 제어기를 생성함. 
                3. 이 제어기가 실제 가상 컨테이너 주머니인 Pod를 1개 생성하여 실행

        2. kubectl get deployments / pods
            - 현재 상태(Current State) 모니터링**
            - 쿠버네티스는 끊임없이 "내가 명령한 상태(Desired State)"와 "컴퓨터에서 실제로 돌아가고 있는 현재 상태(Current State)"가 일치하는지 감시하는 감시 루프(Control Loop)를 돌림. 
            - kubectl get deployments 혹은 kubectl get pods
            - 쿠버네티스 내부 동작: 사용자가 현재 돌아가고 있는 상태를 확인하는 명령어. 
             만약 아까처럼 이미지 이름이 틀려서 `ErrImagePull`이 뜨면, 쿠버네티스는 *"v2를 5대 띄우고 싶은데(원하는 상태), 이미지가 없어서 못 띄우고 있어(현재 상태)"*라는 불일치 상황을 이 명령어를 통해 개발자에게 리포트해 주는 것

        3. kubectl scale --replicas=5
            - 수평 확장(Horizontal Pod Autoscaling / Scale-out)
            - 전통적인 서버 방식(Scale-up)은 동접자가 몰리면 서버 컴퓨터의 CPU와 RAM을 더 좋은 것으로 갈아 끼워야 했음. 
            하지만 쿠버네티스는 동일한 스펙의 작은 Pod를 옆으로 여러 대 더 띄우는 방식(Scale-out)을 취함. 
            Node.js 디자인 패턴에서 강조하는 "싱글 스레드 프로세스를 여러 개 띄워 확장하는 아키텍처"의 인프라 버전! 
            - 내가 한 행동: kubectl scale --replicas=5 deployment hello-web
            - 쿠버네티스 내부 동작: 사용자가 "원하는 복제본(Replicas) 개수를 1개에서 5개로 변경할게"라고 명세를 수정하는 것. 
            이 명령을 받자마자 Deployment의 하부 제어기(ReplicaSet)가 바쁘게 움직여 눈 깜짝할 사이에 똑같은 Pod 4개를 추가로 생성해 `5/5 READY` 상태를 맞춤. 
            
        4. kubectl expose deployment ... --type=LoadBalancer
            - 서비스(Service)와 로드 밸런싱(Load Balancing)
            - Pod는 수시로 죽고 새로 태어남. 스케일링을 하거나 Pod가 에러로 죽어서 새로 켜질 때마다 **Pod의 내부 IP 주소는 계속 랜덤하게 바뀜!!!!.** 주소가 자꾸 바뀌면 클라이언트(브라우저, API 게이트웨이)가 어디로 요청을 보내야 알 수 없음 -> 이 문제를 해결하기 위해 앞단에 고정된 주소(우체통)를 만들어주는 개념이 Service(서비스)다! 
            - kubectl expose deployment hello-web --type=LoadBalancer --port=8080
            - 쿠버네티스 내부 동작:
                1. hello-web`이라는 고정 주소(Service) 객체를 만들.
                2. 이 서비스는 뒤에 숨어있는 Pod 5개에 `app=hello-web`이라는 태그(라벨 사Selector)가 붙어있는 것을 보고 이들을 하나로 묶음
                3. `--type=LoadBalancer` 옵션을 줬기 때문에 외부 트래픽을 받을 수 있는 관문을 열고, 아까 `autocannon`으로 테스트한 것처럼 들어오는 수천 개의 요청을 뒤에 있는 5개의 Pod 주소로 라운드 로빈(Round-Robin) 방식으로 골고루 분산(로드 밸런싱) 해 줌. 

        5. `kubectl set image` 및 `rollout`
            - 무중단 배포(Rolling Update / Rollout)**
            - 서비스를 중단하지 않고 코드를 v1에서 v2로 업데이트하는 기법.
             쿠버네티스는 구버전 서버를 한 번에 다 끄는 게 아니라, "새 버전 서버 하나 켜고 ➡️ 구버전 하나 끄고"를 반복하는 롤링 업데이트 방식을 기본으로 사용함. 
            - kubectl set image deployment/hello-web hello-web=hello-web:v2
            - 쿠버네티스 내부 동작:
                1. Deployment 관리자에게 *"앞으로 배포할 이미지는 v2야"*라고 선언함. 
                2. Deployment는 v2용 새로운 복제본 제어기(ReplicaSet v2)를 새로 만듦. 
                3. `ReplicaSet v2`가 v2 기반 Pod를 1개 띄우면, 기존의 `ReplicaSet v1`이 맡고 있던 v1 기반 Pod 5개 중 1개를 지움.
                4. 이 과정을 점진적으로 반복하여 최종적으로는 서비스 중단(Down-time) 없이 모든 Pod를 v2로 안전하게 교체함!
