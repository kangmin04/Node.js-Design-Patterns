1. 확장성의 세 가지 차원 (The Scale Cube)
① X축 확장: 복제 (Cloning)
    - (X축 확장은 가장 흔하고 구현하기 쉬운 방법) 동일한 애플리케이션 인스턴스를 여러 개 실행.
    - 방법: 애플리케이션의 복사본을 여러 서버(또는 프로세스)에 띄우고, 그 앞에 로드 밸런서(Load Balancer)를 두어 트래픽을 분산시킴
    - 특징: 개발 비용이 적고 즉각적인 효과를 볼 수 있습니다. 만약 인스턴스가 4개라면, 각각 전체 트래픽의 약 25%씩을 담당하게됨. 
    - 한계: 데이터베이스 자체가 병목이 되거나, 애플리케이션의 복잡도가 너무 높을 때는 이 방법만으로 해결되지 않습니다.

② Y축 확장: 서비스/기능 분해 (Decomposing)
    - Y축 확장은 애플리케이션을 기능이나 역할에 따라 여러 개의 독립적인 서비스로 쪼개는 것
    - 방법: 하나의 거대한 앱을 '사용자 인증 서비스', '결제 서비스', '상품 관리 서비스' 등으로 분리합니다. 이것이 흔히 말하는 **마이크로서비스 아키텍처(MSA)**의 핵심입니다.
    - 특징: 각 서비스는 독립적으로 개발, 배포, 확장이 가능합니다. 특정 기능(예: 결제)에만 트래픽이 몰릴 경우 해당 서비스만 별도로 확장할 수 있어 효율적입니다.  
    - 효과: 코드의 복잡성을 줄이고, 여러 팀이 동시에 다른 서비스를 개발할 수 있어 조직의 확장성도 높아집니다.

③ Z축 확장: 데이터 파티셔닝 (Data Partitioning)
    - Z축 확장은 인스턴스마다 담당하는 데이터의 영역을 나누는 것입니다.
    - 방법: 모든 인스턴스가 모든 데이터를 다루는 것이 아니라, 특정 기준(사용자의 국가, 이름 알파벳 순, ID의 해시값 등)에 따라 요청을 특정 인스턴스로 보냅니다.
    - 특징: 주로 데이터베이스 레벨에서 샤딩(Sharding)이라는 이름으로 많이 쓰이지만, 애플리케이션 레벨에서도 적용 가능
    - 효과: 데이터 규모가 너무 커서 하나의 인스턴스가 전체를 감당할 수 없을 때 매우 강력합니다. 대규모 글로벌 IT 기업들이 주로 사용하는 고급 전략입니다.


2. 수직적 확장(Vertical) vs 수중적 확장(Horizontal)
 - 수직: HW적으로 확장(  작업이 많아졌을 때, 기존 서버의 성능 자체를 업그레이드하는(예: CPU, RAM 사양을 높임) 방식)
 - 수평: SW적 확장( 처리해야 할 작업이 많아졌을 때, 서버의 대수를 늘려서(예: 1대 → 4대) 요청을 나누어 처리하는 방식)

3. Node.js와 확장성
 - Node.js는 확장성에 있어 독특한 철학을 가지고 있다
 - 싱글 스레드의 특성: Node.js의 자바스크립트 실행은 싱글 스레드. 따라서 최신 멀티코어 CPU의 성능을 100% 활용하려면 기본적으로 여러 개의 프로세스를 실행(X축 확장)해야 함. 
 - 강제적인 좋은 습관: Node.js는 처음부터 "어차피 여러 인스턴스를 돌려야 한다"는 전제를 깔고 가기 때문에, 개발자는 자연스럽게 무상태(Stateless) 설계를 지향하게 된다. 
 - 예시 (세션 관리): 서버 메모리에 세션을 저장하면, 다른 인스턴스로 접속한 사용자는 로그아웃된 것처럼 보입니다. 이를 방지하기 위해 Node.js 개발자들은 초기부터 Redis 같은 외부 저장소에 세션을 저장하는 방식을 선호하게 됨. 


4. CLUSTER모듈
 - Node.js는 기본적으로 싱글 스레드로 작동하므로, 멀티코어 시스템의 성능을 모두 쓰려면 코어 수만큼 프로세스를 띄워야 한다. (X축 확장!)
   이를 자동화해주는 것이 cluster 모듈임. 
 - 하나의 기본 프로세스(Primary Process)가 여러 개의 워커 프로세스(Worker Process)를 생성(fork)한다. 
 - Primary Process: 워커들을 관리하고 외부에서 들어오는 네트워크 연결을 수신하여 워커들에게 배분
 - Worker Process: 실제 애플리케이션 로직을 실행하고 요청을 처리함. 각 워커는 독립된 프로세스이므로 자신만의 메모리 영역을 가짐
 - 로드 밸런싱 알고리즘: 라운드 로빈 (Round-Robin)
 - 일반적으로 한 포트(예: 8080)는 하나의 프로세스만 점유할 수 있다. 하지만 클러스터 모듈에서는 여러 워커가 동일한 포트를 리스닝하는 것처럼 보임. 이는 워커가 직접 리스닝하는 것이 아니라 Primary 프로세스에 위임하기 때문이다. 
   워커가 listen()을 호출하면 실제로는 Primary에게 "포트를 열어달라"고 요청
   Primary가 해당 포트를 잡고 있다가, 연결이 들어오면 워커에게 전달합니다.

 - cluster은 내부적으로 child_process.fork() 사용하여 워커 프로세스 생성한다. 
 child_process는 여러 프로세스 띄우면 서로 다른 포트 사용. BUT 클러스터는 Primary 프로세스가 대표 포트 리스닝 후 워커에게 라운드 로빈방식으로 분배함. 

 - cluster은 왜 프로세스를 사용할까? 
 node의 설계 철학은 상태를 공유하지 말라는 것. 
 전통적 스레드 모델은 메모리 공유하며 경쟁상태나 교착상태(Dead Lock) 발생 가능 
 Node는 메모리 격리를 함. -> 멀티 스레드 사용 불가. 
 => 멀티 코어 활용을 위해 멀티프로세스를 적용. (여러개의 독립적 프로세스 실행)

즉, 워커가 독립적 프로세스면 한 worker의 문제는 격리된 메모리 공간 내애서만 발생하여, 다른 worker은 영향 안받음. 종료된 worker은 primary 프로세스에게 알리고, 대체 프로세스를 생성. 
BUT 워커가 종속적인 스레드면 한 워커에서 오류가 생기면 다른 워커 스레드들도 전부 해당 문제된 데이터를 공유하기에, 전체 시스템이 멈춤 


 - cluster.workers: Primary 프로세스에서만 접근가능함. 현재 활성화된 모든 Worker 프로세스에 대한 참조. 


    5. KILL: Signal을 전송하는 시스템 콜
        - kill <PID>: 특정 프로세스 ID(<PID>)에게 **신호(Signal)**를 보내는 Unix/Linux 명령어입니다. 
        이름과 달리 꼭 '죽이는' 것만을 의미하지는 않습니다. 
        프로세스에게 특정 이벤트를 알리는 '알림' 기능에 가깝습니다.
        
        - SIGKILL: "무조건 강제 종료해!" (거부 불가능)
          SIGTERM: "정중하게 종료해줘." (기본값, 정상 종료 시도)
          SIGUSR2: "사용자 정의 신호 2 (User-defined Signal 2)". 이 신호는 미리 정해진 기능이 없습니다. 이것이 핵심입니다. 개발자가 애플리케이션 코드 내에서 이 신호를 받았을 때 어떤 동작을 할지 직접 정의할 수 있다.
          SIGINT: Signal Interrupt. 하던 일 멈추라는 신호. (Crtl + C는 현재 실행중인 프로세스에게 SIGINT 시그널을 보내라고 지시하는 단축키)
        
        보낼 때: KILL -SIGUSR2 PID 형식으로 ! 

  ㅇ PM2
    - 프로세스 관리자. 
    - 기존 node app.mjs로 직접 실행 시 문제: , 
        1. 터미널 세션에 프로세스가 종속됨. (터미널 종료 시 서버도 종료)
        2. 에러 발생 시 서버 그대로 중단 
        3. CPU코어 여러개여도 하나의 프로세스만 사용됨. 멀티 코어활용을 위해선 직접 cluster 모듈 사용해야함. 
    - pm2 start app.mjs -i max로 실행 시 
        1. pm2가 알아서 app을 백그라운드에서 실행시켜줌
        2. pm2가 내부적으로 cluster 모듈을 사용하여 현재 device의 CPU 코어 수만큼 자동으로 프로새스 복제 및 실행함. 
        3. 각 프로세스로 들어오는 요청을 자동으로 로드밸런싱해줌. 
        4. 즉, 복잡한 cluster 모듈을 관리할 필요 없이, 순수 비즈니스 로직에만 집중하면 됨. 
        5. 워커 프로세스 죽으면 자동으로 재시작. 
        6. pm2 reload all로 서비스 중단없이 새로운 버젼으로 업데이트 가능
        7. pm2 monit, pm2 logs로 관리 가능
        
    - 기본(fork): pm2 start app.mjs -> 하나의 프로세스만 생성
      cluster: pm2 start app.mjs -i max -> 최대 코어 개수로 프로세스 생성
    - pm2 monit, logs 시 cpu 사용량, mem(메모리 사용량), Heap size(V8엔진이 이 프로세스 위해 확보한 전체 힙 메모리 크기), Heap Usage(현재 사용중인 힙 메모리의 비율), Event Loop Latency(이벤트 루프가 한바퀴 도는데 걸리는 시간. 얼마나 빨리 도느냐가 중요)
    - fork 시 mem 사용량은 작으나, CPU 병목에 취약하여 Event Loop Latency가 높을수도
      cluster 시 mem 높으나, Event Loop Latency가 낮음. 
      추가로 cluster의 경우, 프로세스 간 데이터 공유가 필요한 경우 Redis 등을 사용해야함. 


  ㅇ CPU, CORE, Process
  CPU: 모든 계산, 명렁어 실행이 일어나는 중앙처리장치(두뇌) 
  CORE: 실제 연산을 하는 독립된 계산 유닛. 
    1개의 CPU가 1개의 코어: 싱글코어 
    1개의 CPU가 2개의 코어: 멀티코어 
    1개의 CPU가 4개의 코어: 쿼드코어 
  PROCESS: 
  - 운영체제에서 실행 중인 프로그램의 인스턴스. 자신만의 독립된 메모리 공간을 가짐.
  코어와 프로세스의 관계:
    - **동시성 (Concurrency):** 1개의 코어는 여러 프로세스를 아주 짧은 시간 단위로 번갈아 실행(시분할)하여 동시에 실행되는 것처럼 보이게 할 수 있다. 즉, 한 코어는 하나의 작업만 하지만, 여러 작업을 매우 빠르게 번갈아가며 실행하기에 동시에 실행되는거처럼 보인다. (실제로 매 순간엔 오직 한 코어당 한 프로세스만 점유)
    - **병렬성 (Parallelism):** 4개의 코어는 4개의 프로세스를 물리적으로 '진짜 동시에' 실행할 수 있다.
    - `pm2 start -i max`는 CPU의 코어 개수만큼 프로세스를 생성하여 **병렬성**의 이점을 극대화하는 명령어이다.
    현대의 모든 OS는 병렬성, 동시성을 동시에 사용하여 시너지를 냄. 


ㅇ Daemon (데몬)
         - 정의: 사용자와 직접적인 상호작용 없이, 운영체제의 백그라운드에서 실행되는 프로세스.
           - 핵심 특징: 터미널 세션에 종속되지 않아, 터미널을 종료해도 프로그램은 계속 실행됨.
         - 왜 필요한가? (문제점)
           - `node server.js`로 직접 실행 시, 프로세스는 터미널의 '자식'이 됨.
           - 터미널(부모)이 종료되면, 자식인 `node` 프로세스도 함께 종료되어 서버가 중단됨.
         - 데몬의 역할: "프로세스 독립시키기"
           - 프로세스를 터미널 세션으로부터 '분리(detach)'시켜, 시스템 자체에 직접 속하게 만듦.
           - 이를 통해 컴퓨터가 켜져 있는 동안 계속해서 프로그램이 동작하도록 보장함.
         - PM2와 데몬의 관계:
           - `pm2 start` 최초 실행 시, `God Daemon`이라는 PM2 자체 데몬이 백그라운드에 생성됨.
           - 이 `God Daemon`이 우리가 실행시킨 `app.mjs` 같은 자식 프로세스들을 생성하고, 죽지 않도록 감시하고 관리함.
           - `pm2 list`, `pm2 logs` 같은 명령어는 백그라운드의 `God Daemon`에게 상태를 물어보는 통신 수단임.
         - 데몬화 과정: 
            1. 프로세스 복제
            2. 부모 프로세스 즉시 종료 
            3. 자식 프로세스는 고아가 됨. 
            4. OS는 최상위 프로세스인(PID1)에 자동으로 입양 -> 터미널과는 관계없는 독립적인 프로세스
    
 ㅇ IPC vs. Redis (프로세스 간 통신/공유)
         - 목적, 범위, 확장성에서 근본적인 차이가 있음.
         - IPC (process.on / process.send):
           - 목적: 메시지 전달 (Messaging) 및 신호(Signal) 송수신.
           - 비유: 마스터-워커 간의 1:1 내부 전화 통화.
           - 범위: 단일 서버 내의 마스터-워커 프로세스 간으로 한정!!! 
           - 데이터: 데이터의 '복사본'이 전달됨 (메모리 직접 공유 X).
           - 확장성: 수평적 확장(서버 추가) 불가능.(IPC는 단일 서버 내에서만 작동함 -> 서비스 확장으로 서버 한대 더 추가할 경우, 해당 서버와는 IPC 통신 불가. )
           - 사용 예: PM2가 내부적으로 `reload` 명령을 워커에게 전달할 때 사용.
           ( IPC의 send: 
            1. 직렬화(워커가 변경한 데이터를 Primary Process에게 전달 시 바이너리 형태 등으로 직렬화, CPU 사용됨)
            2. 프로세스 간 통신(IPC, os 커널을 통해 Primary Process에게 전달) 
            3. 역직렬화(받은 데이터를 다시 JS 객체로 변환. CPU 사용됨)
            4. IF 내가 생각했던거처럼, 부모가 자식에서 전체 Broadcast 한다면, 다시 데이터를 N번 직렬화, IPC N번 호출, N번 역직렬화 해야함....... -> 상당한 병목
            그래서 공유를 위해선 redis 사용하는게 합리적. 
            )
         - Redis (외부 중앙 저장소):
           - 목적: 상태 공유 (State Sharing).
           - 비유: 모든 직원이 보고 쓰는 '사무실 중앙 화이트보드'.
           - 범위: 네트워크 전체. "다른 서버"의 프로세스와도 공유 가능.
           - 데이터: 모든 프로세스가 '하나의 원본'을 참조함 (진정한 상태 공유).
           - 확장성: 수평적 확장의 핵심. 서버가 늘어나도 상태를 일관되게 유지!!!!! 
           - 사용 예: 사용자 세션 관리, DB 캐싱, 실시간 순위표 등.
         - 결론:
           - IPC는 PM2가 내부적으로 사용하는 '내부 통신망'.
           - Redis는 클러스터/분산 환경에서 상태를 공유하기 위한 '외부 중앙 저장소'. 둘은 상호 대체 불가능함.

  ㅇStateful Communications
    authenticated 시 instance A에서 정보를 저장했으면, 그 다음 요청이 instance B로 갈 경우, B에는 정보가 없기에, 해당 인증 로직이 작동안됨. 
    -> 문제 !! (authentication state가 local로 저장될 경우, application은 multiple instances에 대해 안정성있는 서비스가 안됨)

    solution 1. shared db(PostgreSql, MongoDb, COuchDb 혹은 in-memory store인 Redis, Memcached)
    단점: require significant amount of refactoring of the codebase. 
    (shared data store은 scalable, reliable application을 위해 preferred 되는 선택지임. trade-off는 cost와 complexity. )

    solution 2. sticky load balancing. 
      - refactoring이 불가능할경우(시간 제한, too many changes 등으로)
      - load balancer가 session과 server instance 정보를 저장해두고, 해당 session으로 들어오면 무조건 해당 서버로 전달하는것. 
      - 장점: 코드 수정없이 여러 서버 환경에서 동작가능. 
      - 단점: 특정 서버에 유독 무거운 작업을 고정시켜 과부하(불균등)될수있음. 
              특정 사용자의 고정된 서버가 다운되면, 그 사용자 세션 정보는 완전히 소실됨. 
              서버 동적추가, 제거 작업이 복잡해짐. 
      => 메모리에 상태를 저장하는 레거시 어플리케이션 확장 시 유용. BUT 확장가능 및 안정적인 최신의 경우, 서버를 stateless 로 만들고, redis 등 중앙공유 저장소에서관리하는게ㅐ 바람직. 

      - sticky load balancing 동작 방식 2가지. 
          1. 쿠키 (일반적)
            클라이언트가 app.com(예시) 접속
            -> 현재 브라우저는 app.com에 대한 쿠키가 아무것도 없음. 그냥 get 요청만 보냄
            -> 로드밸런서가 요청 받고, 자신이 발행한 세션 쿠기가 없으니 rr알고리즘으로 서버 결정 후 해당 서버에게 요청 보냄. 
            [응답과 쿠기 생성과정]
            -> 서버는 요청 처리하고, 웹페이지 생성하고, 응답을 보냄
            -> 해당 응답은 로드밸런서를 우선 거침
            -> 로드밸런서는 응답을 가로채서 헤더 수정함(보낸 서버 정보를 쿠기로 추가함. Set-Cookie: SERVERID=instance-A; path=/)
            -> 해당 응답이 브라우저로 전달됨. 
            [클라이언트의 2번째 요청 ]
            -> 브라우저가 app.com에 요청 보내기 전, 자신이 저장하고있는 쿠키를 우선 체크
            -> 쿠키에 아까 저장한 instance-4가 있으므로 요청헤더에 쿠키를 포함하여 보냄
            -> 로드밸런서에서 해당 쿠키 확인 후 고정된 라우팅으로 보냄. 

          2. IP 주소 해싱. 
            클라이언트 IP 주소 기반으로 해시값 계산하여 서버와 매핑함. 
            IP가 변경되지않는 이상, 항상 같은 서버로 접속됨. 
            신뢰도 적음. (모바일 네트워크는 IP가 자주 바뀌고, 회사의 경우 여러 사용자가 같은 공인 IP를 사용하기도함.. )
      - 위의 모든 과정은 애플리케이션 코드레벨에서가 아닌, 로드밸런서에서 설정함. AWS의 Application Load Balancer(ALB)
      

    - 위의 방법들은 stateful한 서버에서 하는것.. -> 차라리 session state가 필요없는 JWT가 선호됨. 
     ㅇ JWT (JSON Web Token) 기반 인증: 완전한 무상태(Stateless) 구현
             - 정의: 사용자의 인증 정보와 권한 등을 담은 '정보 객체'를 JSON 형태로 만들어, 서버의 비밀 키로 '서명'한 암호화된 토큰.
             - 핵심 아이디어: 서버는 상태를 저장하지 않고, 클라이언트가 모든 상태 정보(토큰)를 가지고 다니게 한다.
             
             - 전통적 세션 방식 vs. JWT 방식
                 - 세션 방식 ("놀이공원 손목 티켓"): 서버가 "123번 티켓은 John"이라는 장부(상태)를 직접 보관하고 매번 확인해야 함. (메모리에 직접 저장(Stateful) 또는 외부 저장소(redis) 필요)
                 - JWT 방식 ("위조 불가능한 신분증"): 서버는 신분증(JWT)을 발급만 해주고 바로 잊어버림. 어떤 서버든 신분증 자체의 유효성(서명, 만료기간)만 검증하면 됨. (Stateless)
             
             - JWT 구조: Header.Payload.Signature
                 - Header: 토큰 타입, 서명 알고리즘 등 메타데이터.
                 - Payload: 실제 전달할 내용 (사용자 ID, 권한, 만료 시간 등).
                 - Signature: Header와 Payload를 서버의 '비밀 키(Secret Key)'로 암호화한 값. **JWT 보안의 핵심.**
                 
             - JWT 보안: 위조(Forgery) vs. 탈취(Theft)
                 1. 위조 방지 (내용 수정 불가)
                     - 공격자가 Payload의 내용을 1비트라도 수정하면 (`"role":"user"` -> `"role":"admin"`), 서버만 아는 '비밀 키'가 없으므로 올바른 서명(Signature)을 다시 만들어낼 수 없음.
                     - 서버는 토큰 수신 시, 서명을 다시 계산하여 일치 여부를 확인하므로 위조된 토큰은 즉시 거부됨.
                     
                 2. 탈취 대응 (토큰 도난)
                     - 문제점: JWT는 '소유자가 임자(Bearer Token)'이므로, 유효한 토큰이 탈취되면 공격자가 주인 행세를 할 수 있음.
                     - 대응 전략:
                         ① 짧은 만료 기간 (Short Expiry Time): Access Token의 유효 기간을 5분, 15분 등으로 매우 짧게 설정하여 탈취 시 피해 최소화. (가장 중요)
                         ② 리프레시 토큰 (Refresh Token) 패턴: 유효기간이 긴(예: 7일) Refresh Token을 별도로 발급. Access Token이 만료되면 이 Refresh Token으로 조용히 새 Access Token을 재발급받아 사용자 경험을 유지.
                         ③ HTTPS 통신 필수: 네트워크 중간에서 토큰을 엿보는 '중간자 공격(MITM)'을 원천 차단.
                         ④ (심화) 토큰 폐기 목록: 로그아웃, 비밀번호 변경등으로 더 이상 안쓰는 무효화된 토큰 목록을 Redis 등에 저장하여, 요청 시마다 해당 목록을 한번 더 확인하는 방식. (완벽한 Stateless를 약간 포기하고 보안 강화)
                         
             - 결론: JWT는 서버의 상태 저장 책임을 완전히 제거하여, 어떤 서버 인스턴스가 요청을 처리하든 일관된 인증을 제공함. 이는 로드 밸런싱, 오토 스케일링, 마이크로서비스 아키텍처 환경에서 확장성을 극대화하는 가장 선호되는 방식임.


     ㅇ Stateful vs. Stateless 서버: 분산 시스템의 핵심 개념
         - 정의: 여러 대의 서버(인스턴스)로 서비스를 확장할 때, '상태(State)'를 어디에, 어떻게 저장하고 관리할 것인가에 대한 아키텍처 구분.
         - '상태'란? 사용자의 로그인 정보, 장바구니 내용, 게임 진행 상황, 조회수 등 시간이 지나면서 변할 수 있는 모든 데이터.

         1. Stateful 서버 (상태 유지 서버)
             - 개념: 서버가 이전 요청의 결과나 클라이언트의 상태를 **자신의 메모리 안에** 직접 저장하고 기억하는 방식.
             - 코드 수준 예시:
                 // 서버 프로세스의 메모리 변수에 상태(조회수)를 저장
                 let viewCount = 0; 
                 
                 app.get('/', (req, res) => {
                   viewCount++; // 요청이 올 때마다 자신의 메모리에 있는 값을 변경
                   res.send(`조회수: ${viewCount}`);
                 });
             
             - 문제점: 수평 확장(Scale-out) 시 데이터 불일치 발생
                 - 서버 A와 B, 두 대를 운영할 경우, 각 서버의 viewCount는 별개로 존재함.
                 - 로드 밸런서가 요청을 분산시키면, 사용자는 서버 A의 viewCount(예: 5)와 서버 B의 viewCount(예: 3)를 번갈아 보게 되어 일관성이 깨짐.
                 - 서버 하나가 다운되면, 그 서버의 메모리에 있던 모든 상태(로그인 세션, 장바구니 등)가 소실됨.
             - 해결책: Sticky Session (특정 사용자를 특정 서버에 고정시키는 임시방편)

         2. Stateless 서버 (상태 비저장 서버)
             - 개념: 서버가 요청 처리에 필요한 모든 정보를 요청 자체에서 얻거나, **외부의 공유 저장소**에서 가져옴. 서버 자체는 아무것도 기억하지 않음.
             - 비유: 자판기 (누가, 언제, 무엇을 뽑았는지 전혀 기억하지 않고, 들어온 요청만 처리함)
             - 코드 수준 예시:
                 // 상태 관리를 외부 공유 저장소(예: Redis)에 위임
                 const redisClient = redis.createClient();

                 app.get('/', async (req, res) => {
                   // 상태를 읽고 쓰는 모든 작업을 외부 저장소에 요청
                   const newViewCount = await redisClient.incr('pageViews');
                   res.send(`조회수: ${newViewCount}`);
                 });

             - 장점:
                 - 완벽한 수평 확장성: 어떤 서버가 요청을 처리하든 항상 동일한 외부 저장소를 바라보므로 데이터 일관성이 보장됨. 서버를 수백 대로 늘려도 문제가 없음.
                 - 높은 안정성 및 유연성: 서버 하나가 다운되어도 상태는 외부 저장소에 안전하게 보관되어 있으므로, 다른 서버가 즉시 이어서 작업을 처리할 수 있음.
                 - 서버 배포 및 관리가 단순해짐.

         - 결론: 현대적인 대규모 웹 서비스는 안정적인 확장성과 고가용성을 위해 Stateless 아키텍처를 지향하는 것이 표준. 상태 관리는 Redis와 같은 고속 인메모리 DB나 영구 DB에 위임하는 것이 일반적임.




     ㅇ Socket.IO와 Sticky Load Balancing: 필수적인 조합
         - 문제점: 왜 Socket.IO는 여러 서버 환경에서 그냥 동작하지 않는가?
             - Socket.IO는 클라이언트와 '특정 서버 프로세스' 간의 지속적이고 상태 기반(Stateful)인 연결(주로 WebSocket)을 생성함.
             - 로드 밸런서가 첫 연결 요청(HTTP Handshake)은 서버 A로 보내고, 다음 통신(Polling 등)은 서버 B로 보내면, 서버 B는 해당 클라이언트에 대한 정보를 전혀 모르므로 연결이 즉시 끊김.

         - 해결 방안 1: Sticky Load Balancing (기본이자 필수)
             - 정의: 로드 밸런서가 특정 Socket.IO 세션에서 발생하는 모든 후속 요청을, 첫 연결이 수립된 동일한 서버 인스턴스로만 보내도록 '고정'하는 방식.
             - 동작: 일반적인 쿠키 기반 고정성(Cookie-based Stickiness) 기능을 사용함. 클라이언트의 첫 연결(Handshake)에 대한 응답에 로드 밸런서가 쿠키를 심어주고, 클라이언트는 이후 모든 요청에 해당 쿠키를 포함하여 항상 같은 서버로 찾아갈 수 있게 됨.
             - 한계: 이 방식만으로는 '서버 간 메시지 공유'가 불가능함. 예를 들어 서버 A에 접속한 사용자는 서버 B에서 보낸 메시지(`emit`)를 직접 받을 수 없음. 또한, 고정된 서버가 다운되면 해당 서버에 연결된 모든 클라이언트의 연결이 끊기는 단점은 여전함.

         - 해결 방안 2: Socket.IO 어댑터(Adapter) 사용 (진정한 확장성)
             - 대표 예시: `socket.io-redis` 어댑터.
             - 개념: 모든 서버 인스턴스가 중앙의 Redis Pub/Sub 기능을 구독하여, 서로 메시지를 주고받을 수 있는 통로를 만드는 방식.
             - 동작 원리:
                 1. 서버 A가 특정 방(room)에 메시지를 보낼 때 (`io.to('news-room').emit(...)`), 자신의 클라이언트에게만 보내는 것이 아니라, 연결된 Redis에 메시지를 발행(Publish)함.
                 2. Redis를 구독 중인 다른 모든 서버(B, C, ...)가 이 메시지를 수신함.
                 3. 각 서버는 메시지를 수신한 후, 자신의 서버에 연결된 클라이언트 중 'news-room'에 속한 클라이언트가 있다면 그들에게 메시지를 전달함.
             - 결과: 사용자가 어떤 서버 인스턴스에 접속해 있든, 클러스터 전체에 메시지를 브로드캐스팅할 수 있게 됨.

         - 최종 결론 (Best Practice):
             "Socket.IO를 제대로 확장하려면 Sticky Session과 Redis 어댑터, 둘 다 필요하다."
             1. Sticky Session: 개별 클라이언트와 서버 인스턴스 간의 '연결' 자체를 안정적으로 유지하는 역할. (연결의 안정성)
             2. Redis Adapter: 모든 서버 인스턴스 간에 '메시지'를 자유롭게 공유하고 전파하는 역할. (메시지의 확장성)
             => 이 두 가지를 함께 사용해야만, 안정적이면서도 수평적으로 확장이 가능한 대규모 실시간 애플리케이션을 구축할 수 있음.



     ㅇ Forward Proxy vs. Reverse Proxy: 누구를 위한 대리인인가?(Forward는 클라이언트를 위해! 클라이언트를 숨겨줌.  Reverse는 서버를 위해. 서버를 숨겨줌.)
         - 프록시(Proxy)의 공통점: 클라이언트와 서버 사이에서 요청과 응답을 중계하는 '대리인' 서버.
         - 핵심 차이점: 프록시가 '누구를 위해' 일하는가에 따라 Forward와 Reverse로 나뉨.

         1. 포워드 프록시 (Forward Proxy)
             - 개념: **클라이언트를 위한** 프록시. 클라이언트가 인터넷에 요청을 보낼 때 거쳐 가는 서버.
             - 흐름: `클라이언트 -> [포워드 프록시] -> 인터넷(외부 서버)`
             - 특징: 
                 - 요청을 받는 **최종 서버는 실제 클라이언트의 IP를 알 수 없음.** 오직 포워드 프록시 서버의 IP만 보게 됨. (클라이언트가 숨겨짐)
                 - 주로 내부망(사내 네트워크, 학교망 등)에 속한 클라이언트들이 인터넷에 접근할 때 사용됨.
             - 주요 사용 목적:
                 - **캐싱**: 자주 사용되는 콘텐츠를 프록시 서버에 캐싱하여 내부 사용자들의 접근 속도를 향상.
                 - **보안 및 접근 제어**: 내부망에서 특정 웹사이트(유해 사이트 등)에 접근하는 것을 막는 방화벽 역할.
                 - **익명성**: 클라이언트의 IP를 감추고 인터넷에 접속할 수 있음.

         2. 리버스 프록시 (Reverse Proxy)
             - 개념: **서버를 위한** 프록시. 인터넷의 불특정 다수 클라이언트로부터 오는 요청을 대신 받아 내부 서버로 전달하는 서버.
             - 흐름: `클라이언트 -> [리버스 프록시] -> 내부 서버들 (WAS)`
             - 특징:
                 - **클라이언트는 자신이 요청을 보내는 실제 서버의 IP를 알 수 없음.** 오직 리버스 프록시 서버의 IP(대표 도메인 주소)만 알게 됨. (서버가 숨겨짐)
                 - **Node.js/Express 환경에서 Nginx를 사용하는 것이 바로 이 방식.**
             - 주요 사용 목적:
                 - **로드 밸런싱**: 여러 대의 내부 서버로 요청을 균등하게 분산.
                 - **보안**: 내부 서버의 존재를 숨기고, DDoS 공격 방어, SSL 암호화(SSL Termination) 등을 전담하여 내부 서버를 보호.
                 - **정적 콘텐츠 처리**: 이미지, CSS, JS 등 정적 파일 요청을 리버스 프록시가 직접 처리하여 WAS(Node.js 서버)의 부담을 줄임.
                 - **캐싱**: 자주 요청되는 응답 결과를 캐싱하여 내부 서버로 요청이 전달되지 않게 함으로써 성능 향상.
             - cluster 모듈보다, reverse proxy가 더 선호됨! (프로세스 뿐만 아니라 다른 머신으로도 load balancing가능함. sticky load balancing도 지원 가능. most powerful한 load balancing algorithm 선택 가능)




     ㅇ Cluster 모듈 vs. 리버스 프록시: 무엇을, 언제 사용해야 하는가?
         - 공통점: 둘 다 여러 프로세스에 작업을 분산하여, 싱글 스레드인 Node.js의 한계를 극복하고 성능을 향상시키는 데 사용됨.
         - 핵심 차이: '어떤 레벨'에서 '어떻게' 분산하는가에 대한 스코프와 역할이 완전히 다름.

         1. 동작 방식 및 스코프의 차이

          | 구분 | Cluster 모듈 | 리버스 프록시 (Nginx) |
          | 목적/스코프 | 단일 서버 내의 멀티코어 CPU 활용 극대화 | 여러 서버(머신) 간의 트래픽 분산 |
          | 확장 방향 | **수직 확장 (Scale-up)**: 한 머신의 성능을 최대로 끌어냄 | **수평 확장 (Scale-out)**: 여러 머신으로 부하를 나눔 |
          | 동작 레벨 | **Node.js 프로세스 레벨**: 하나의 앱 코드를 여러 프로세스로 복제 | **네트워크 레벨**: HTTP/TCP 요청을 다른 IP/Port로 전달 |
          | 포트 관리| 하나의 포트를 여러 워커 프로세스가 공유 (Primary가 중계) | 각 앱/프로세스는 **고유한 포트**를 가져야 함 (예: 3000, 3001) |
          | 주요 기능 | - CPU 코어 수만큼 워커 생성<br>- 워커 프로세스 관리 (사망 시 자동 재생성) | - **로드 밸런싱** (다양한 알고리즘)- SSL 암호화 처리- 정적 파일 서빙- 캐싱, 보안, 압축 등 |
          | 장애 대응 | Primary 프로세스가 죽으면 전체 앱 중단 | 서버 하나가 죽어도 다른 서버로 요청을 보내 서비스 유지 가능 |

         2. 그래서 뭘 써야 하는가? (결론 및 권장 아키텍처)
             - 질문 자체가 "A vs B"가 아닙니다. 이 둘은 경쟁 관계가 아닌, **서로 다른 계층에서 협력하는 관계**입니다.
             - **현대적인 프로덕션 환경에서는 이 둘을 '함께' 사용합니다.**

         3. 최종 권장 아키텍처 (Best Practice)
             - "리버스 프록시 + (각 서버별) 클러스터 모듈"
             
             1. **1계층: 리버스 프록시 (Nginx)**
                 - 웹 서버의 '얼굴' 역할을 하며 인터넷의 모든 요청(Port 80/443)을 가장 먼저 받습니다.
                 - SSL 인증서 처리, 정적 파일(이미지, CSS) 서빙, 압축 등을 수행합니다.
                 - 로드 밸런싱 규칙에 따라 내부에서 실행 중인 여러 Node.js 서버(예: 서버1의 3000번 포트, 서버2의 3000번 포트)로 요청을 분산시킵니다.
             
             2. **2계층: Node.js 애플리케이션 (Cluster 모듈 적용)**
                 - Nginx로부터 요청을 받은 각 서버(서버1, 서버2) 내부에서는 `cluster` 모듈이 동작합니다.
                 - `cluster` 모듈은 해당 서버의 CPU 코어 수만큼 워커 프로세스를 생성하여, Nginx로부터 받은 요청을 다시 워커들에게 분배합니다.
                 - 이를 통해 단일 서버의 리소스를 낭비 없이 모두 활용할 수 있습니다.
             
             - 흐름 요약:
                 `사용자 -> Nginx -> [서버1(3000포트), 서버2(3000포트)] 중 하나로 분산 -> 선택된 서버의 Primary 프로세스가 받음 -> 내부 워커 프로세스 중 하나로 분산`

         - 결론: 리버스 프록시는 **여러 대의 서버**로 서비스를 확장하고 안정성과 다양한 부가기능을 제공하기 위해 **필수적**이며, 클러스터 모듈은 **개별 서버**의 성능을 최대한 끌어올리기 위한 **최적화** 기법입니다.
         - 다만 위는 다소 과거의 방식. 현재는 nginx 앞단에 두고 뒤엔 컨테이너 orchestrator(쿠버네티스 등)으로 처리함!

        / (루트 디렉토리)
        ├── bin/      # 기본적인 명령어(ls, cp 등)가 있는 곳 (모든 사용자가 사용)

        ├── etc/      # ★★★ 시스템 전체에 적용되는 '설정(Configuration) 파일'들이 있는 곳
        |             # (예: /etc/nginx/nginx.conf)
        |
        ├── home/     # ★★★ 일반 사용자들의 개인 홈 디렉토리. '우리 집'들이 모여있는 곳
        │   └── user/ # (예: /home/user/workspace/chapters 가 여기에 있을 수 있음)
        |
        ├── usr/      # 일반 사용자를 위한 프로그램과 데이터
        │   ├── bin/  # ( /bin 에 없는 추가적인 프로그램들)
        │   └── local/ # ★★★ 사용자가 직접 컴파일해서 '설치(install)'한 프로그램들이 위치하는 곳
        │       ├── bin/     # (설치한 프로그램의 실행 파일)
        │       └── etc/     # (설치한 프로그램의 설정 파일)
        │       └── nginx/   # (Nginx를 소스 컴파일로 설치했다면 여기에 생김)
        │           └── conf/
        │               └── nginx.conf # ★★★
        |
        └── var/      # 내용이 자주 바뀌는 파일들 (로그, 캐시, 데이터베이스 파일 등)
            └── log/
                └── nginx/
                    ├── access.log
                    └── error.log

  ㅇ NGINX 
    - homebrew로 설치함. 
      Homebrew를 사용하면 복잡한 설치 과정이나 의존성(이 프로그램을 깔기 위해 다른 프로그램이 필요한 상황)을 자동으로 해결해 주며, 
      Mac의 시스템 폴더를 건드리지 않고 안전한 전용 폴더(/opt/homebrew/ 또는 /usr/local/)에 프로그램들을 모아서 관리해준다. 

    - /opt/homebrew/etc/nginx/nginx.conf는 Homebrew가 Nginx를 설치하면서 만들어둔 글로벌(기본) 설정 파일임. 
       터미널에 그냥 nginx라고만 입력하고 엔터를 치면, Nginx는 자동으로 이 글로벌 경로에 있는 nginx.conf를 읽어서 서버를 켠다. 
       현재 진행 중인 프로젝트에 특화된 설정을 글로벌 파일에 덮어쓰면, 나중에 다른 프로젝트를 할 때 설정이 꼬일 수 있음 -> 따라서 지금처럼 프로젝트 폴더 안에 나만의 nginx.conf를 따로 만들어서 관리하는 것(로컬 설정)이 훨씬 실무적이고 안전한 방식! 

    - 터미널에서 ${PWD}는 비밀번호가 아닌, 현재 파일의 폴더 경로임. 
    nginx -c ${PWD}/nginx.conf 로 실행. 

    - 다만, nginx -c ${PWD}/nginx.conf 시 access_log, error_log 위치를 못찾음. 
        1. /logs/error_log.log 면 -> 가장앞에 /기에 root 에서 찾으란 소리! 당연히 없음, 
        2. log/error_log.log면 -> homebrew가 설치해둔 경로인, /opt/homebrew/Cellar/nginx/1.31.2/logs/nginx-access.log에서 찾으려하나, 당연히 없음! 
        3. 해결책: 실행 시  nginx -p ${PWD} -c ${PWD}/nginx.conf 로 -p 옵션을 줌 -> nginx에게 현재 프로젝트 폴더가 nginx의 홈 디렉토리라는걸 알려줌!!! log 가능하다. 


  ㅇ Dynamic Horizontal scailing. 
    - cloud pattern
    - application capacity가 traffic에 따라 실시간으로 조절됨. 
      (예시) (확장 규칙) "만약 모든 서버의 평균 CPU 사용률이 5분 동안 70%를 넘으면, 서버를 2대 더 늘려라."
            (축소 규칙) "만약 평균 CPU 사용률이 5분 동안 20% 미만으로 떨어지면, 서버를 1대 줄여라."
    - infrastructure cost는 줄이고, application을 반응성있게 해줌. 
    - 한계: load balancer이 어떤 서버가 가용가능한지 항시 알아야함. (always up-to-date! )
    위의 always up-to-date(항상 최신상태 유지) 한계를 해결하기 위해 service registry 적용! 
    service registry는 자동으로 갱신되는 주소록같은거임.

ㅇ 서비스 레지스트리 (Service Registry): 동적 환경의 '자동 갱신 주소록'
    - 개념: 클라우드의 동적 수평 장 환경에서, 끊임없이 생성되고 사라지는 서비스 인스턴스(서버)들의 최신 네트워크 위치(IP, 포트)를 중앙에서 관리하고 알려주는 '주소록' 또는 '내비게이션' 시스템.
    - 역할: 실제 사용자 요청을 중계하는 로드밸런서가 아니라, 로드밸런서나 다른 서비스가 "어디로 요청을 보내야 하나요?"라고 물어봤을 때 길을 알려주는 역할을 함. (요청 경로에 직접 관여하지 않음)

    - 왜 필요한가? (문제점)
        - 오토 스케일링으로 서버 IP와 포트가 계속 바뀌기 때문에, 로드밸런서 설정 파일에 주소를 수동으로 적어두는 것이 불가능함.
        (클라우드 환경 기반이 되면서 서비스가 autoscailing(시스템 자원 모니터링하며 서버 늘리거나 줄임)으로 동적으로 생성되거나, 컨테이너 기반 배포로 서비스의 IP가 동적으로 변경되는게 잦아짐)
        
    - 핵심 동작 방식:
        1. 서비스 등록 (Service Registration):
           - 새로운 서버 인스턴스가 시작되면, 스스로 자신의 서비스 이름, IP, 포트 정보를 서비스 레지스트리에 등록함.
           - "저 '주문 서비스'의 새 인스턴스입니다. 주소는 10.1.2.3:8080 이에요."
        2. 서비스 탐색 (Service Discovery):
           - 로드밸런서가 요청을 전달하기 전에, 서비스 레지스트리에 특정 서비스(예: '주문 서비스')의 현재 가용한 인스턴스 목록을 물어봄.
           - "지금 사용 가능한 '주문 서비스' 주소 목록 좀 주세요."
        3. 건강 상태 확인 (Health Checking):
           - 서비스 레지스트리는 등록된 인스턴스들이 정상적으로 작동하는지 주기적으로 확인하여, 고장 난 인스턴스는 목록에서 자동으로 제거함. 이를 통해 장애가 발생한 서버로 요청이 전달되는 것을 방지.

    - "Decoupling(분리)"의 의미:
        - 서비스 레지스트리를 사용하면, 로드밸런서는 서비스의 실제 물리적 위치(IP 주소)에 대해 전혀 알 필요가 없게 됨.
        - 로드밸런서는 오직 서비스의 논리적인 이름('주문 서비스')만 알고 있으면 되며, 실제 서버가 10대가 되든 100대가 되든 신경 쓸 필요가 없어짐.
        - 이처럼 서비스의 '소비자'와 '제공자'를 분리하여, 동적인 환경 변화에 유연하게 대처할 수 있게 하는 것이 핵심 가치.

    - 대표 도구: Consul, Netflix Eureka, etcd, Apache ZooKeeper

    - service Discovery: 클라우드 환경에서 서비스 클라이언트가 서비스를 호출할 때 서비스의 위치(IP, PORT 번호) 알아낼 수 있는 기능. 
        1. Client Side Discovery(P2P 방식)
              - 작동 순서
                1. Service instance 생성 될 때, IP/PORT/서비스명이 Service Registry에 등록
                2. Service Client가 Service Registry에 QUERY 보냄. (서비스 위치 받고자! )
                3. Registry는 서비스 위치를 반환해줌. 
                4. 클라이언트 내부의 로드밸런싱 알고리즘을 통해 서비스를 호출함. 
        2. Server Side Discovery(Load balancer 활용 방식)
              - CLient Side Discovery에서 Service Client위치에 Load Balancer을 둠. 
              이후 Client가 load balancer호출하고, load balancer은 위와 동일한 과정을 해줌. 
                

  ㅇ Consul
    - Consul은 강력한 기능들을 미리 만들어진 HTTP API 엔드포인트 형태로 제공하며, 우리는 그저 문서에 정의된 규칙에 따라 해당 주소로 HTTP 요청을 보내기만 하면됨.  

    - portFinder로 여러 포트 찾아서 node app.mjs web 을 여러번 실행하는건, 멀티 프로세스임. 
    각 명령어 시 새로운 프로세스가 생성되고 독립된 메모리 공간을 받음. 
    8081과 8082는 서로 영향을 안줌! -> 회복탄력성(하나가 죽어도 다른건 영향 안받고, Consul이 하나 죽은걸 감지해서 더 이상 거기로 트래픽 안보내게됨) 
  

  ㅇ Peer-to-Peer (P2P) 로드 밸런싱

  -  개념: 중앙에 별도의 로드 밸런서 없이, 요청을 보내는 **클라이언트가 직접** 여러 서버 중 하나를 선택해 연결하는 분산형 방식. 로드 밸런싱 로직이 클라이언트 측에 포함됨.

  -   기본 구현 (정적 목록 방식)
      -   클라이언트 코드 내에 서버 목록(호스트, 포트)을 하드코딩.
      -   `Round-Robin`과 같은 간단한 알고리즘으로 다음 요청을 보낼 서버를 순차적으로 선택.
      -   문제점:
          1.  **유연성 부족**: 서버 추가/제거 시 모든 클라이언트의 코드를 수정하고 재배포해야 함.
          2.  **장애 감지 불가**: 특정 서버가 다운되어도 클라이언트는 계속해서 해당 서버로 요청을 보내게 되어 장애가 발생함.


  ### P2P 로드 밸런싱 vs. 중앙 집중식 로드 밸런싱 (Reverse Proxy)

  1.  **P2P (클라이언트 측) 로드 밸런싱**
      -   **장점**:
          -   **낮은 지연 시간**: 중앙 로드 밸런서를 거치지 않아 네트워크 홉(hop)이 줄어듦.
          -   **비용 효율**: 로드 밸런서를 위한 별도의 인프라 비용이 없음.
          -   **SPOF(단일 장애점) 없음**: 로드 밸런서 자체가 고장 날 위험이 없음.
      -   **단점**:
          -   **복잡한 클라이언트**: 로드 밸런싱, 서비스 디스커버리 로직이 클라이언트에 포함되어 복잡도 증가.
          -   **관리의 분산**: 로직이 모든 클라이언트에 흩어져 있어 일관성 유지 및 업데이트가 어려움.
      -   **주요 사용 사례**: **마이크로서비스 아키텍처(MSA) 내부의 서비스 간 통신**에 매우 효과적.

  2.  **중앙 집중식 로드 밸런싱 (e.g., NGINX, AWS ELB)**
      -   **장점**:
          -   **중앙 관리**: 로드 밸런싱 정책, 라우팅 규칙, 보안 등을 한곳에서 관리.
          -   **고급 기능**: 정교한 라우팅(경로 기반, 헤더 기반), SSL/TLS 처리, 웹 방화벽(WAF), 캐싱 등 강력한 기능 제공.
          -   **단순한 클라이언트**: 클라이언트는 로드 밸런서의 대표 주소만 알면 됨.
      -   **단점**:
          -   **추가 비용 및 인프라**: 로드 밸런서 자체를 위한 비용과 관리가 필요.
          -   **네트워크 홉 추가**: 모든 요청이 로드 밸런서를 거치므로 약간의 지연 시간 추가.
          -   **SPOF 가능성**: 로드 밸런서 자체의 고가용성(HA) 구성이 필수적.
      -   **주요 사용 사례**: **외부 인터넷 사용자로부터 들어오는 모든 트래픽**을 처리하는 단일 진입점(Single Point of Entry) 역할.


    - 실무에선 Kubernates가 consul의 기능을 대체함! 
    쿠버네티스를 사용하면 consul이 지원하던 service Discovery, health check, 부하분산 전부 해줌. 
    다만, 과도기나 레거시 회사등 모든 회사가 쿠버네티스를 쓰는건 아니니 consul을 그땐 사용하면돔. 

 ㅇ MSA 흐름 
    사용자가 쇼핑몰 앱에서 "주문하기" 버튼을 눌렀을 때, 시스템 내부에서 일어나는 일. 

    - 1단계: 외부 요청 진입 (Nginx / API Gateway)
        하는 일: 사용자의 요청(HTTP)을 가장 먼저 맞이하는 대문
        이유: 외부 사용자는 내부 구조(어떤 서비스가 어디에 있는지)를 알 필요가 없다. 오직 하나의 주소만 보고 요청을 보냄
        흐름: "주문해 줘!"라는 요청이 들어오면, API 게이트웨이가 URL을 보고 "아, 이건 주문(Order) 서비스로 가야 하는구나" 판단해서 길을 열어줌. 

    - 2단계: 자동 스케일링과 처리 (Kubernetes)
        하는 일: 컨테이너(Pod)의 개수를 조절하고 내부로 요청을 전달함
        이유: 블랙 프라이데이처럼 주문이 폭주하면 주문 서비스 서버가 터질 수 있겠죠?
        흐름: 쿠버네티스가 주문 서비스의 CPU 사용량이 치솟는 걸 보고, 주문 서비스 컨테이너를 기존 2대에서 5대로 알아서 늘림(Auto-scaling). 게이트웨이가 보낸 요청은 이 늘어난 컨테이너들로 골고루 분산되어 안전하게 처리됩니다.

    - 3단계: 서비스 간의 내부 통신 (gRPC)
        하는 일: "서비스끼리의 통신"
        이유: 주문 서비스 혼자서는 주문을 완료할 수 없습니다. 고객의 '결제'도 해야 하고, 결제가 끝나면 '배송' 서비스에도 알려야 함. 즉, 주문 서비스가 결제 서비스와 배송 서비스를 호출해야 한다!!!! 
        흐름 (여기서 gRPC 등장): 주문 서비스가 결제 서비스에게 "이 고객 결제 좀 진행해 줘" 라고 요청을 보낼 때, 굳이 무겁고 느린 HTTP JSON 통신을 쓸 필요가 없다. 
        이때 내부 전용 초고속 고속도로인 gRPC를 사용해 컴퓨터 내부 함수를 호출하듯이 아주 빠르고 가볍게 결제 서비스에 요청을 찌르는 것! 
        이때 전 단계에서 말씀드린 'P2P 로드 밸런싱'이 작동하여, 주문 서비스가 결제 서비스의 여러 컨테이너 중 가장 한가한 녀석에게 직접 요청을 보낸다. 


    - 꼭 GRPC를 사용하는 이유?? 
    : 난 처음에 결국 로컬에서 서버의 함수를 실행하는 것이니, 그냥 로컬에도 동일한 함수를 두면 안되나? 생각했다. 
    그러나, 로컬에 두는 것과 grpc를 사용하는건 완전히 목적이 다르다. grpc는 내 컴퓨너가 아닌, 네트워크 건녀편의 다른 서버의 컴퓨너에게 일을 시키는 기술이다. 

    쇼핑몰 서비스의 경우, 주문 서비스와 결제서비스가 분리되어있다. (비즈니스 로직 구분하여 독립적 배포 위해서! MSA의 특징)
    만약, 주문 서비스에서 원격의 결제 서비스를 불러올 때 내 생각처럼 로컬(주문서비스코드)에서 결제 서비스의 결제 코드를 작성한 후 호출한다면 ...
    -> MSA는 서비스마다 전용 dB가 있기에 주문 서비스에서 결제 Db에 접근이 불가능함! 
    + 또한 결제 정책 변경으로 수수료 등이 변경될 땐 모든 마이크로 서비스( 주문, 취소, 결제 서비스 등)을 수정하고 배포해야하는대ㅔ, 이는 MSA 핵심이 독립적 배포가 불가능해짐. 
    
    결론: 즉, 로컬에 함수 복사하는건 코드 모양만 따라하는 것이고, 실제 격리된 서버의 자원(DB, 메모리)에 접근이 불가함! -> 네트워크를 타고 넘어가서 진짜 결제 서버에 일을 시켜야함 -> GRPC!! 
    
    - HTTP대신 GRPC?? 
    : 다른 서버 호출은 axios.get('http://pazment-service/pay') 같은 HTTP REST API 방식도 있다.
    그럼에도 gRPC를 사용하는 이유? 
        1. IDL (Interface Definition Language)을 통한 강력한 타입 보장
            - proto buffer을 통해 호출하는 쪽에서 잘못된 데이터 타입 넣으면 컴파일 시점이나 실행 직전 로컬에서 에러를 잡아버림. 서버 간 통신에서 데이터가 다를 확률을 0%
            - 반면 REST API는 주문 서비스가 결제 서비스로 데이터를 보낼 때 오타가 나거나(quantitiy: 1), 숫자가 아닌 문자열(quantity: "한개")을 보내면 받는 쪽 서버에서 에러가 나거나 크래시가 남. 
        2. 압도적인 속도와 효율성 (Protocol Buffers + HTTP/2)
            - REST API: JSON을 주고받음 -> 데이터가 커지면 무겁고, 복호화에도 시간 오래 걸림. 
            - gRPC: 이진 데이터(Binary)로 압도적으로 압축(Protocol Buffers 기술)해서 보냄. 
                    게다가 기본 네트워크 프로토콜로 HTTP/2를 사용하기 때문에 하나의 연결 통로로 수많은 요청과 응답을 동시에 주고받을 수 있다.
            즉, 내부 서비스끼리 수초 내에 수천 번 통신해야 하는 MSA 환경에서 REST API보다 수 배에서 수십 배 빠르고 CPU 자원을 훨씬 적게 먹음. 
        3. 정말 로컬함수를 쓰는듯한 개발자 경험
            - 별도의 부호화/복호화, 에러핸들링, TCP 통신 신경 쓸 필요없이, gRPC가 네트워크 통신부분을 감추기에 편하게 코딩 가능 


    - 실제 코드 예시(쿠버네티스 + gRPC)

    1. protobuffer
        syntax = "proto3"; // 1️⃣ 구문 버전 설정

        package order;     // 2️⃣ 패키지(네임스페이스) 정의

        // 3️⃣ 서비스 및 RPC 메서드 정의: (orderRequest)타입을 인자로 받아서 OrderResponse 타입을 반드시 반환한다는 약속
        service OrderService {
        rpc CreateOrder (OrderRequest) returns (OrderResponse);
        }

        // 4️⃣ 메시지(데이터 구조) 정의: 필드태그 설정. gRPC는 JSON 처럼 item:노트북 이렇게 보내는게 아닌, 1번 필드의 값은 문자열 노트북이다처럼 binary로 보내기에 압도적으로 빠름. 
        message OrderRequest {
        string item = 1;
        int32 quantity = 2;
        }

        message OrderResponse {
        string message = 1;
        string processed_by = 2;
        }

    2. 클라이언트 (요청 보내는 곳 api-gateway.mjs)
        const grpc = require('@grpc/grpc-js');
        const protoLoader = require('@grpc/proto-loader');
        const express = require('express');

        // 1️⃣ proto 파일 로드 및 파싱 (컴파일 하는 과정)
        const packageDefinition = protoLoader.loadSync('order.proto', {});
        const orderProto = grpc.loadPackageDefinition(packageDefinition).order;

        const app = express();

        // 2️⃣ 🌟 핵심: gRPC 클라이언트(스텁, Stub) 객체 생성(네트워크 통신을 대행해줄 가짜 서버 객체. 이 객체로 마치 로컬 함수인거처럼 createOrder 호출 가능)
        const client = new orderProto.OrderService(
        'dns:///order-service-internal:50051', // 쿠버네티스와 연동 부분! dns:/// 로 하면, gRPC 라이브러리가 쿠버네티스 내부 DNS 시스템에 *"이 이름(order-service-internal)을 가진 Pod들의 IP 주소를 싹 다 대조해서 가져와 줘"*라고 요청
        grpc.credentials.createInsecure(), // 보안(SSL) 없이 가볍게 연결하겠다는 뜻
        {
            'grpc.service_config': JSON.stringify({
            loadBalancingConfig: [{ round_robin: {} }]
            })
            // gRPC의 클라이언트 사이드 로드 밸런싱 메서드 옵션. 
            //쿠버네티스 DNS를 통해 대상 Pod가 3대(10.0.1.2, 10.0.1.3, 10.0.1.4) 켜져 있는 것을 확인하면, 중간 로드 밸런서 없이 gRPC 클라이언트 자체가 내부 알고리즘(round_robin)을 돌려 1번, 2번, 3번 Pod로 요청을 직접 번갈아 가며 P2P 분산 발송함! 
        }
        );

        // 3️⃣ Express 라우터 안에서 gRPC 메서드 호출: 첫 인자로 객체 넘기면, gRPC가 즉시 이진데이터로 인코딩 후 HTTP/2파이프라인을 통해 전송하고, 저 멀리서 처리가 끝나고 돌아온 응답 데이터를 두 번째 콜백 인자인 response로 깔끔하게 받음. 
        app.get('/order-test', (req, res) => {
        client.CreateOrder({ item: '노트북', quantity: 1 }, (err, response) => {
            if (err) return res.status(500).json({ error: err.message });
            res.json(response);
        });
        });

    3. 서버 (요청받아 처라하는 쪽)order-services.mjs 
        const grpc = require('@grpc/grpc-js');
        const protoLoader = require('@grpc/proto-loader');
        const os = require('os');

        const packageDefinition = protoLoader.loadSync('order.proto', {});
        const orderProto = grpc.loadPackageDefinition(packageDefinition).order;

        // 1️⃣ 실제 비즈니스 로직을 수행할 서비스 함수 구현: gRPC 서버가 요청을 받았을 때 실행할 함수. 
        function createOrder(call, callback) {
            console.log(`요청 수신함: ${call.request.item}`);
            
            // 성공 응답 전송 (첫 번째 인자는 에러객체, 두 번째는 응답 데이터)
            callback(null, {
                message: `${call.request.item} 주문이 완료되었습니다.`,
                processed_by: `서버 호스트네임: ${os.hostname()}`
            });
        }

        // 2️⃣ gRPC 서버 인스턴스 생성 및 서비스 등록
        const server = new grpc.Server();
        server.addService(orderProto.OrderService.service, { createOrder });

        // 3️⃣ 서버 바인딩 및 구동
        server.bindAsync('0.0.0.0:50051', grpc.ServerCredentials.createInsecure(), () => {
            console.log('주문 내부 서비스 구동 완료 (Port 50051)');
            server.start();
        });


 
  ㅇ Monolithic architecture
    - 모놀리틱 구조라고 해서, 모듈이 없거나 모든 서비스가 연결된게아님. 
    모듈을 가지는 구조도 있고 decoupling이 잘된 경우도있음. 
    [ ex ] Linux OS kernel
        : Monolithic kernel, microkernel 존재함... 
        (Monolithic의 경우, kernel mode에서 전체 서비스 작업(프로세스 관리, 메모리 관리, 파일 시스템, 네트워크 등)이 일어남
            장점: 서비스간 데이터 교환이나 함수 호출이 매우 빠르고 오버헤드 거의 없음. 
            단점: 한 작업의 오류가 전체 OS down으로 이어질수있음)
        (microkernel의 경우, only 코어 서비스(IPC, 메모리 관리)만 kernel mode에서 작업하고, 나머지(파일 시스템, 장치 드라이버 등)는 usermode에서 실행됨.
            장점: crash나도 전체 시스템엔 영향 없음
            단점: 유저모드에서 실행 중인 서비스가 커널의 기능 사용하거나, 다른 서비스와 통신하려면 커널 모드로 전환(컨텍스트 스위칭)과 프로세스 간 통신(IPC) 발생)


    [ ex ] e-commerce application 의 경우, 한 어플리케이션 내에 store-frontend, admin-frontend / 서비스 모듈: products, cart, checkout, search, auth / DB
    => 같은 codebase 내에 존재하고, 한 application으로 실행된다면 이건 Monolithic architecture이다! 
       즉, 한 컴포넌트에서 오류 시 전체 쇼핑몰이 down 될수도있음. 
       각 모듈 간 interdependence가 증가하고 유지보수 어려워짐. 



  ㅇ Microservice architecture
    - building large-scale Nodejs system에서 가장 중요한 건, DO NOT BUILD LARGE SCALE NODEJS SYSTEM. 
    => scale cube의 Y-axis! (break the system down by service and functionality)
    하나의 큰 어플리케이션이 아닌, 작고 focused components로 .. 

    [ ex ] e-commerce application 의 경우, 
    store-frontend도 하나의 application. 
    admin-frontend도 하나의 application. 
    product service + db
    cart service + db
    checkout service + db
    auth service + db 
    로 구성됨. 
    => independent entity이며, own content 속 own db를 가짐. 
    
     db를 모든 서비스 마다 가지는걸 data ownership이라고 함. 
     data ownership은 micro service의 큰 특징. 
     shared db면 서비스 구현은 쉽지만, 서비스 간 coupling이 생기고 여러 application을 돌리는 것의 강점이 사라짐. 
     
    Microservice advantage
     - 수정이 필요한 경우에도, 서비스 전체가 아닌ㄴ 해당 서비스만 변경하면됨 -> 간편. 
     - resuability. 
     
    Microservice disadvantage
     - manage할 node들이 증가한 것이기에, integration / deployment / code sharing 등에 higher complexity가 생길수있음. 
       => cloud service와 devops methodologies, nodejs 패턴으로 해결 가능 ! 
     
     
    Integration pattern in Microservice
        - 마이크로서비스는 모든 서비스들은 collaborate(연결) 시켜야함. 
        [ ex: e-commerce의 경우 Cart service를 위해선 products 서비스가 필요하고, Checkout을 위해선 Cart 서비스가 필요하며, Search 서비스의 경우 products 서비스가 필요함 ]
        - integration strategy 디자인 시 coupling도 고려해줘야함. resuability, extensibility 등을 고려해야함. 

        1. API PROXY pattern
            - api proxy를 앞단에 두고 로드밸런싱처럼 해당 서비스로 전달해줌. 
            - 서비스들의 복잡성을 숨겨줌. 
            - 다만, 여러 서비스를 하나로 묶어주는 구조적인 역할만 할 뿐, 데이터의 의미를 이해하고 가공하는 로직은 없음(non semantic) 
        2. API Orchestration
            - store frontend application 
              
              API Orchestration layer (completeCheckout(), cancelCheckout(), addToCart() 등 ... )
                
                

              checkout-service             cart-service          product-service

              으로 application 나누고, 
              frontend 단에서 checkout 요청 시 
              1. api Orchestration layer에서 checkoutService/pay 형태로 REST API 호출하여 transaction 실행
              2. payment 성공한 경우, cart에서 구매한 아이템을 제거 해야하기에 cartService/delete 호출하여 아이템 제거. 
              3. 이후 product의 availability도 변경해줘야 하기에 productService/update 호출하여 제품 목록 변경. 

            - orchestrator은 흐름만 제어하고, 실제 비즈니스 로직은 각 마이크로서비스가 알아서 처리함.

            장점: 
            - store frontend와 decouple됨. 
            - api Orchestration은 semantic integration을 함!   
            (API 프록시: "클라이언트가 /products를 요청했네? products-service로 그대로 전달해줘야지." (단순 중계, Structural Integration)
             API 오케스트레이션: "클라이언트가 '주문 상세 정보'를 요청했네? 알았어, 내가 ①orders-service에서 주문 정보를 가져오고, ②그 주문에 포함된 상품 ID로 products-service에 상품 정보를 물어본 다음, ③두 정보를 예쁘게 합쳐서 한 번에 줄게." (의미를 이해하고 조합, Semantic Integration))
            - 여러 서비스를 거치는데, api orchestrator로 명확하게 파악 및 관리 가능. 
            - 쉽게 design, debug, scale 가능함

            단점: 
            - 구조와 서비스가 어떻게 진행되는지에대한, complete knowledge가 필요함. 
            - god object 처럼 한 객체가 tpp much work를 해서 high coupling, low cohension, high complexity를 초래하는 상황 발생할수있다. 

            MSA 관련 추가 자료(BFF) : 
            - 만약, 각 frontend가 distinct requirement를 가질경우(다른 디바이스 간 ..(모바일, PC, 워치끼린 제공하는 데이터 형태가 달라야할수도있음)) -> BFF 패턴. (Backend for Frontend)
              여러 디바이스들에 대해 하나의 큰 API가 아닌, 각 frontend별로 본인만의 backend를 가지며, 백엔드들은 프론트에서 원하는 형태로 데이터 전달 가능. 
            
            
            3. Messaging Pattern
            - API Orchestration의 단점인 high coupling과 시스템의 complexity를 보완하고자 하는게 messaging pattern임! 
            - centralized Publish/Subscribe pattern... 
            ex: 
            1. store frontend에서 checkoutService/pay api invoke. 
            2. 결제 종료 후 , checkout-service에서 위의 작업에 대한 세부 내용을 담은 이벤트를 발행! (event: 'purchased', cardId: '1', products:[...])형식 // checkout-service 발행자가 메시지를 order_events 토픽으로 발행함. 이떄, checkout-service는 누가 메세지 받을지 모름. 
            3. message broker가 order_events 토픽으로 들어온 메시지를 수신. 
            4. 브로커가 구독자 목록을 확인함. cart-service가 이전에 브로커에게 order_events토픽을 구독 신청했음 
               Notification-service도 order_events 토픽을 구독 신청했습니다. (이유: 고객에게 '주문 완료' 이메일을 보내야 하므로)
               Product-service는 이 토픽에 관심이 없어서 구독 신청을 하지 않았습니다.
            5. 브로커가 cart-service와 Notification-service 두 곳 모두에게 메시지르 ㄹ전달함. 
            product-service에겐 전파안함. 

            - decouple됨!! 
              관심사가 분리되어 checkout-service는 결제 처리에만 집중하고 결제 끝났다고 외치기만 하면됨. 
              특정 서비스가 새로 생긴다면 해당 서비스를 order_events 토픽을 구독하게 하면, 별도의 코드 수정없이 확장 가능함. 


## Consul 헬스 체크 (Health Check) 

    - 단순히 서비스가 켜져있는지(is-alive)를 넘어, 정상적으로 요청을 처리할 수 있는 상태인지(is-healthy)를 주기적으로 검사하는 기능.
    - 헬스 체크에 실패한 서비스는 서비스 디스커버리 결과에서 자동으로 제외되어, 장애가 발생한 인스턴스로 트래픽이 전달되는 것을 원천 차단함.
    - 이를 통해 시스템이 스스로 장애를 감지하고 복구하는 **회복성(Resiliency)**과 **자가 치유(Self-Healing)** 능력을 갖추게 됨.
 
     #### 1. 헬스 체크 등록 방법
    - 서비스 등록 시 `Check` 객체를 포함하여 Consul Agent에게 "이 규칙대로 서비스를 감시해줘" 라고 지시함.
Line 800:     
Line 801:     ```json
Line 802:     {
Line 803:       "Name": "user-service-a-d",
Line 804:       "ID": "user-service-a-d-instance-1",
Line 805:       "Port": 8081,
Line 806:       "Tags": ["user-service", "a-d"],
Line 807:       "Check": {
Line 808:         "HTTP": "http://localhost:8081/health",
Line 809:         "Interval": "10s",
Line 810:         "Timeout": "1s",
Line 811:         "DeregisterCriticalServiceAfter": "30s"
Line 812:       }
Line 813:     }
    ```
  - **HTTP**: 체크를 수행할 API 엔드포인트.
   - **Interval**: 체크를 수행할 주기. (예: 10초마다)
    - **Timeout**: 응답을 기다리는 최대 시간. 이 시간 내 응답이 없으면 실패로 간주. (예: 1초)
   - **DeregisterCriticalServiceAfter**: 서비스가 'Critical' 상태로 이 시간 이상 지속되면, 레지스트리에서 자동으로 완전히 제거함. (예: 30초)
   
   
   #### 2. 상태 판정 규칙 (Convention)
    - Consul은 HTTP 응답 코드를 기준으로 서비스의 건강 상태를 판단함. 이는 Consul과 우리 서비스 간의 약속임.
   
   - **`2xx` (예: 200 OK):** 정상 (Passing) - 서비스가 건강함.
   - **`429 Too Many Requests`:** 경고 (Warning) - 서비스가 과부하 상태일 수 있음.
   - **그 외 모든 코드 (4xx, 5xx):** 실패 (Critical) - 서비스에 문제가 발생함.

   
     #### 3. 장애 발생 시 시나리오 (자가 치유 과정)
   
1.  **장애 발생:** 8081번 포트의 서비스에 내부 오류가 발생하여 `/health` 요청에 `500` 에러를 응답하기 시작.
2.  **실패 감지:** Consul 에이전트가 10초 주기 체크 중 `500` 응답을 받음.
3.  **상태 변경:** Consul은 즉시 `user-service-a-d-instance-1` 서비스의 상태를 **'Critical'**로 변경함.
4.  **트래픽 중단:** 이 순간부터 API 오케스트레이터가 Consul에 서비스를 문의하면, Consul은 'Critical' 상태인 8081번 인스턴스를 결과에서 제외하고 응답함. -> **장애 전파 차단!**
5.  **자동 제거:** `DeregisterCriticalServiceAfter`에 설정된 30초 동안 서비스가 복구되지 못하면(계속 'Critical' 상태이면), Consul은 해당 서비스를 레지스트리에서 **완전히 삭제**함.

=> 이 모든 과정이 관리자의 개입 없이 자동으로 이루어지며, 시스템 전체의 안정성을 크게 향상시킴.



  ㅇ API orchestrator 추가 구현
    1. LOGGING / MONITOR (winston, pino)
        - 요청, 응답에 대한 정보 남김. (요청수, 평균 응답시간, 에러율 등의 metric) -> 전체 시스템의 상태를 한눈에 파악 + 문제 발생시 원인 신속하게 추적가능
        => winston. 
            - 로그를 여러 곳에 저장 가능 (Console, File, HTTP, Database)
            - 로그의 심각도를 단계별로 나눌수있음 
            -------------------------------------------
           
    2. Error Handling / Resilence (opossum)
        - 특정 백엔드 인스턴스 서버 다운 시, 해당 서버로 요청 보내는걸 일시 중단하여, 하나의 장애가 전체 장애로 번지는 Casacading Failure 방지! 
        => circuit breaker pattern
        - 처음엔 consul의 health check기능이 있는데 굳이 왜 필요하나 생각했다. 
          그러나 opossum은 외부 서비스 호출로 인해, 클라이언트가 장애를 겪지않는것이 목적. 
          실패가 임계치 넘으면 추가 요청없이, 즉시 실패 시켜 내 어플리케이션의 리소스를 보호하고 응닶시간 단축함. 
          또한, 서킷 브레이커는 서버의 품질저하도 캐치 가능(네트워크 지연 혹은 과부하로 서버가 느려진 경우, consul은 health를 반환하지만, 서킷은 일정 timeout 초과 시 실패로 간주함)
          consul은 서비스 계속 비정상이면 파괴하고, 서비스 복구 시 스스로 re-register 해야함. 일시적 장애 상황보단 영구적으로 종료한 상황이 발생한 경우 더 유리함. 
          반면 opossum은 일정 시간 회로 끊은 후 다시 요청 보냄. 성공하면 CLOSED로 상태 변경 후 정상작동함

        - 서킷브레이커는 API orchestrator인 LB에구현되어야함. 만약 요청보낸 a-d가 작동안할경우, api에서 관리할것이기에!  




  ㅇ winston
    - 로그하면 좋은 것 추가 : 
        1. 성공한 요청들에 대해서도 + 얼마나 걸렸는지 로그! 
        2. 요청 시작 시 로그 (incoming req)
        3. 프록시 된 응답의 경우, proxyres 이벤트를 사용하여 프록시 응답 시 로그하자! 
        4. 기타 에러들(logger.warn, logger.error)
            에러 시 두번째 인자로 req.url, req.ip 등 자세하게 기록하자! 

    - 예시. 
            const logger = winston.createLogger({
                // 'info' 레벨 이상의 로그만 기록합니다 (info, warn, error)
                level: 'info',
                
                format: combine(
                    colorize(), // 로그 레벨에 따라 색상 적용
                    timestamp({ format: 'YYYY-MM-DD HH:mm:ss' }), // 시간 자동 기록
                    logFormat // 위에서 정의한 포맷 사용
                ),
                // 모든 로그에 'load-balancer'라는 서비스 이름을 기본으로 추가합니다.
                defaultMeta: { service: 'load-balancer' },
                // 로그를 어디에 저장할지 설정합니다.
                transports: [
                    new winston.transports.Console()
                    // 필요하다면 파일로도 저장할 수 있습니다.
                    // new winston.transports.File({ filename: 'error.log', level: 'error' }),
                    // new winston.transports.File({ filename: 'combined.log' })
                ]
            })
            ---------------------------------------------
            이후 logger 모듈 import 하여 logger.info(message, 속성). 
            1단계: 초기 info 객체 생성 winston은 먼저 info라는 기본 객체를 만듭니다. logger.info의 첫 번째 인자는 message가 되고, 두 번째 객체 인자의 속성들은 그대로 info 객체에 합쳐집니다.

            // 최초 생성된 info 객체
            {
            level: 'info',
            message: 'Request successful',
            durationMs: 150
            }

            // defaultMeta 병합 후
            {
            level: 'info',
            message: 'Request successful',
            durationMs: 150,
            service: 'load-balancer' // <--- 추가됨

            // timestamp 통과 후
            {
            level: '\x1B[32minfo\x1B[39m', // 색상 코드가 입혀진 level ]]

            durationMs: 150,

    - Node.js의 req(http.IncomingMessage)와 res(http.ServerResponse) 객체는 매우 복잡하며, 내부에 자기 자신이나 서로를 참조하는 순환 구조를 가짐
     예를 들어, req.socket 객체는 req 객체를 다시 참조할 수 있습니다.
     res 객체도 내부적으로 req 객체와 연결되어 있습니다.
      => Converting circular structure to JSON이라는 에러를 발생시키며 프로세스가 멈추게 됩니다. 
      (console.log의 경우, 순환 참조 시 [circular] 등의 텍스트로 표시하기에 에러 안남)
      => 해결책 req, res 전체 로깅이 아닌, 필요한 정보만 뽑아서 로깅 !! (req.method, req.url 등 .. )

  ㅇ git에서 특정 파일 수정을 취소하고, 그 전 커밋 상태로 돌아가고 싶을 떄 ! 
    => git checkout -- file 
    해당 파일을 저장하지않고 닫기 혹은 마지막 버젼으로 되돌리기 기능임  
    
    - 반면, git checkout <commit>으로 커밋 이동 시엔, 변경대상이 프로젝트 전체고, HEAD가 브랜치가 아닌 특정 커밋을 가리키게되는 Detached Head 상태가 됨. 
      과거 코드를 둘러보는 시간 여행용이지, 여기서 수정을 하는건위험! 

    - 여러 파일 수정 시 ... 
    : git checkout -- fileA.js fileB.css fileC.html
    - src 폴더 내, 모든 변경사항 취소 시 
    : git checkout -- src/
