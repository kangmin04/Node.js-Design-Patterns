# 프록시 패턴의 3가지 구현 방식: Composition, Object Literal, Augmentation

## 1. 개요

세 방식 모두 **원본 객체(Subject)의 기능을 확장하거나 제어**하는 동일한 목표를 가지지만, 접근 방식과 장단점이 명확하게 다름

## 2. 비교 요약

| 구분 | Proxy with Composition | Proxy with Object Literal | Object Augmentation |
| :--- | :--- | :--- | :--- |
| **핵심 아이디어** | 원본 객체를 **멤버 변수**로 포함하는 새로운 프록시 객체를 생성 | 원본 객체를 참조하는 **새로운 객체 리터럴**을 생성 | **원본 객체 자체를 직접 수정** |
| **원본 객체 수정 여부** | **아니오** (원본은 그대로 유지) | **아니오** (원본은 그대로 유지) | **예** (원본을 직접 변경하여 위험) |
| **구현 방식** | 프록시가 원본을 감싸도록(wrap) 인스턴스화 (ES6 `Proxy` 사용 시 가장 강력) | 모든 메서드를 수동으로 위임하는 새로운 객체 리터럴 반환 | 원본 객체의 메서드를 새 함수로 덮어쓰기 |
| **장점** | - 원본을 격리하여 안전<br>- 재사용성 높음<br>- 유연하고 강력함 | - 개념이 단순하고 명시적<br>- 간단하게 구현 가능 | - 특정 메서드만 수정할 때 가장 간단 |
| **단점**| - 간단한 작업에는 코드가 다소 길어질 수 있음 | - 모든 메서드를 수동 위임해야 해서 번거로움<br>- 유지보수 어려움 | - **부작용(Side Effect) 발생 위험 매우 높음**<br>- 디버깅이 어려워짐 |

## 3. 상세 설명 및 사용 가이드

### 1. Proxy with Composition (컴포지션) - ⭐ 가장 권장

- **핵심 아이디어**: 원본 객체를 '소유'하는 새로운 프록시 객체를 만들어, 원본을 안전하게 격리하고 제어합니다. 클라이언트는 프록시와 상호작용합니다.
- **특징**: 원본의 불변성을 보장하며, ES6 `Proxy`와 함께 사용 시 `get`, `set` 등의 트랩(trap)을 이용해 모든 상호작용을 가로챌 수 있어 매우 유연하고 강력합니다.
- **사용 시점**:
    - 보안, 로깅, 캐싱, 접근 제어 등 **체계적인 부가 기능**이 필요할 때.
    - 원본 객체의 코드를 수정하고 싶지 않을 때.
    - 복잡한 제어 로직을 구현해야 할 때.

### 2. Proxy with Object Literal (객체 리터럴)

- **핵심 아이디어**: 원본 객체를 클로저(closure)로 참조하는 새로운 객체를 리터럴 방식으로 생성합니다.
- **특징**: 개념이 가장 단순하고 코드가 명시적입니다. ES6 `Proxy` 같은 고급 기능 없이 간단히 래퍼(wrapper)를 만들 수 있습니다.
- **사용 시점**:
    - 프록시할 메서드의 개수가 적고, 인터페이스 변경이 거의 없는 **간단한 상황**에 적합합니다.
- **단점**:
    - 원본의 모든 메서드를 수동으로 위임 코드를 작성해야 해서 번거롭습니다.
    - 원본 객체에 메서드가 추가/변경되면 프록시 객체도 함께 수정해야 해서 유지보수가 어렵습니다.

### 3. Object Augmentation (객체 증강 / Monkey Patching) - ⚠️ 주의 필요

- **핵심 아이디어**: 원본 객체 자체의 메서드를 직접 수정하여 덮어씁니다.
- **특징**: 가장 간단해 보이지만, **원본 객체를 직접 변경**하여 매우 위험합니다.
- **사용 시점 (매우 제한적)**:
    - **테스트 환경**: 다른 모듈의 동작을 임시로 바꾸는 모킹(mocking)을 할 때.
    - **최후의 수단**: 수정 불가능한 외부 라이브러리의 동작을 불가피하게 변경해야 할 때.
- **단점**:
    - 코드의 다른 부분에 **예상치 못한 부작용(side effect)**을 유발할 수 있습니다.
    - 시스템 전체를 불안정하게 만들고 디버깅을 매우 어렵게 만듭니다.
    - **절대 일반적인 애플리케이션 로직에 사용해서는 안 됩니다.**

## 4. 결론

- **🥇 대부분의 경우**: `Proxy with Composition` (특히 ES6 `Proxy` 활용)을 사용하세요. 가장 안전하고 유연하며 확장성이 뛰어납니다.
- **🥈 간단한 경우**: `Proxy with Object Literal`은 명시적이고 이해하기 쉬운 코드가 필요할 때 좋은 선택입니다.
- **🥉 사용 금지 (예외적 허용)**: `Object Augmentation`은 가능한 한 피하고, 테스트를 위한 모킹 등 특수한 목적에만 제한적으로 사용하세요.

    - 데코레이터 패턴의 핵심은 객체의 코드를 수정하지 않고, 동적으로 새로운 책임(기능)을 추가하는 것
      wrap 하며 새로운 기능을 더한 객체로 사용함. 
    - 데코레이터는 원본 객체와 동일한 인터페이스(메서드 목록)를 제공해야 한다. 
    - 데코레이터는 기존 원본 객체 수정은 안하면서, 기능 확장은 가능. (OCP)
    - 프록시와 유사하나, 데코레이터는 기능추가에 중점을 두고있고, 프록시는 접근제어(원본객체 접근 시 가로채서 로깅, 캐싱, 지연로딩 등을위해) 사용. 
    - 원본과 동일한 인터페이스를 가지기에, 여러개를 겹쳐서 쌓을수있음. 
        // 예시
        const calculator = new StackCalculator();

        // 클라이언트는 최종적으로 포장된 객체를 사용
