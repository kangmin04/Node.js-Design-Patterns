
1. Messaging and integration pattern의 필요성 
    - 12챕터에서 MSA(split application across multiple processes and machines) 배움, 
    서로 Communicate 필요할 때 있음 !! 
    -> 1. shared storage 사용하거나 2. message exchange하는 방식 존재 
    - messaging은 분산 시스템에서 scalability 및 flexibility에 대해 상당히 유용함. 
    - messaging구현은 broker, p2p, one-way OR request/reply, queues 등으로 가능 ! 


2. Fundamental of message system
    - direction of Communication (one-way OR request/reply)
        ① one-way : webserver이 연결된 브라우저에서 message 보내는 행위, system이 workers에게 task distribute하는 것 
        ② request/reply: db에 쿼리 보내는 것. (Communication channel이 async하거나, multiple nodes 대상으로 할 경우 복잡해짐 !)
    - purpose of message (message type)
        ① Command Message (명령 메시지)
            - 의미: 수신자에게 "특정한 행동을 수행하라"고 지시하는 메시지입니다.
            - 성격: 의도(Intent) 중심입니다.
            - 특징:
                요청자가 수신자가 무엇을 해야 하는지(어떤 작업을 수행해야 하는지)를 명확히 알고 있습니다.

                보통 1:1 통신(한 명의 수신자)을 전제

                명령이 실패할 경우, 호출자는 에러 응답을 기대하거나 재시도를 고려해야 함

            - 예: CreateOrder, SendEmail, DeleteUser. + REST API에서 GET, PUT 등의 명렁어들, Remote Procedure Call 

        ② Event Message (이벤트 메시지)
            - 의미: 시스템 내에서 "이미 발생한 사실(Fact)"을 알리는 메시지
            - 성격: 결과(Past Tense) 중심입니다.
            - 특징:
                과거에 일어난 일을 알리는 것이므로 '상태 변경'에 대한 통지입니다.
                발행자는 누가 이 이벤트를 처리할지, 몇 개의 서비스가 처리할지 관심이 없습니다(결합도 극단적 감소).
            - 예: OrderCreated, EmailSent, UserDeleted. + chat 앱에서 누가 어떤 channel로 메세지 보냈는지 이벤트 발생시키고, connected된 user들에게 broadcast됨

        ③ Document Message (문서 메시지)
            - 의미: 시스템 간에 "데이터의 상태(State) 자체"를 전달하는 메시지입니다.
            - 성격: 데이터(State) 중심입니다.
            - 특징:
                상태의 최신 정보(Snapshot)를 전달하여 수신자가 자신의 데이터를 동기화하도록 돕습니다.
                수신자는 이 문서를 바탕으로 자신의 로직을 수행할지 말지 결정합니다. 
                No instruction attached.. 
            - 예: ProductCatalogUpdated (변경된 상품 상세 정보 전체 전달), UserAccountDetails (사용자 변경 정보 전체 전달).
    - timeing of message (sync, async)
    - delivery of message ( directly OR via broker)

3. semantics of Communication channel
    ① Pull delivery(consumer이 data request보냄.)
        - consumer이 언제 data fetch할지 control 가능. -> producer side의 complexity 줄여줌. 
        - pros: 
            ⓐ simpler, debug쉽고, resource usage를 더 predictable하게끔 함. 
            ⓑ cost effective
        - cons: 
            ⓐ adds delay, frequent polling으로 인해 서버 부하 증가 등. 
        - 예시: 
            1. 브라우저가 서버에 웹 페이지 필요할 때 요청 
            2. 서버가 필요할 때 db에 쿼리 보냄    
    ② push delivery(producer이 data를 proactively하게 보냄)
        - consumer의 요청 기다림 없이, real time으로 전달됨. 
        - pros: 
            ⓐ information이 consumer에게 immediately하게 전달되어야 할 때 유용 ! (chat, 실시간 가격 등)
            ⓑ low latency 
        - cons: 
            ⓐ connection관리 , 재시도, backpressure 등에 대해 복잡성을 추가하고, resource-intensive 하게 함.. 


    => 많은 시스템에선 hybrid로 함!  
    (long polling, push Notification 등.. )


4. sync message / async message
    - sync message: 
        - tight coupling. 
        - participant 둘다 동시에 connected이며 하나가 끊어지면 나머ㅓ지도 끊어짐. 
    - async message: 
        - decoupling. (sender, receiver은 서로 동시에 available 할 필요 없으며 message는 저장됐다가 receiver이 ready된 경우 deliver함.)
        - 구현 방법: 
            ⓐ MQ(Message Queue) 
                - consumer busy, disconnected, crashed 등의 경우 queue가 message accept하고 store함. 
                  consumer이 online일 경우, 받은순서대로 consumer에게 보냄 
                - queue는 producer side에서 p2p 형식으로도 가능하고, 혹은 third-party인 message broker에서 조절될수도 있음
            ⓑ log OR stream
                - queue와 비슷한 목적이지만, trade-off존재. 
                - stream은 append-only이며, consumer이 read 가능, 
                - 차이 
                    1. Queue는 메세지가 한번 consumed되면 사라지지만, stream에선 processed 이후에도 accessible 함! go back하여 historical data read 가능
                    2. queue는 주로 point to point방식으로 한 consumer 대상으로 message 전달함. Stream은 multi-subscriber 대상. 여러 consumers이 independently로 같은 msg read 가능. 
                    = > stream은 같은 이벤트에 대해 multi-components들이 대응 가능함. 

5. nodes들 간 연결! (last element to consider in messaging system)
    ① peer-to-peer
        - 모든 노드들이 서로의 receiver의 port, address를 알아야함. 
          또한 프로토콜과 message format에 대한 동의가 있어야함
            ⓐ 프로토콜: 
                - 메시지 형식 (Data Format): 메시지를 어떤 구조로 보낼 것인가? (예: JSON, XML, 직접 정의한 바이너리 형식 등)
                - 전송 방식 (Transport): 어떤 기술을 사용해 네트워크로 메시지를 보낼 것인가? (예: 단순 TCP/IP 소켓, HTTP 요청, UDP 등)
                - 메시지 의미 (Semantics): 특정 메시지가 어떤 동작을 의미하는가? (예: 'CREATE_USER'라는 문자열을 받으면 사용자 생성 작업을 수행)
                - 에러 처리 및 보장 수준 (Error Handling): 메시지 전송 실패 시 어떻게 할 것인가? (재시도? 무시?), 메시지를 받았다는 응답(ACK)을 보낼 것인가?
                - 서비스 탐색 (Discovery): 통신할 상대방의 주소(IP, Port)를 어떻게 찾을 것인가?
        - 장점: 
            
    ②broker 
        - p2p 방식의 복잡함을 제거함! 
        - 모든 node는 independent하고, 서로의 정보를 모른채로 여러 peer과 communicate 가능. 
        - protocol또한 표준 프로토콜 중에 선택하면 됨. p2p처럼 직접 구현할 필요 없음. 
            ⓐAMQP (Advanced Message Queuing Protocol):
                특징: 신뢰성 높은 메시징을 위한 '고급' 프로토콜. 복잡한 라우팅 규칙, 트랜잭션 등 엔터프라이즈급 기능을 많이 제공
                주요 사용처: 금융 시스템, 안정적인 백엔드 서비스 간 통신 (주로 RabbitMQ 브로커가 사용)
            ⓑMQTT (Message Queuing Telemetry Transport):
                특징: 매우 가볍고(Lightweight) 단순한 발행/구독(Pub/Sub) 모델의 프로토콜. 적은 전력과 낮은 네트워크 대역폭을 사용하도록 설계되었습니다.
                주요 사용처: IoT 기기, 모바일 앱 푸시 알림 등 리소스가 제한적인 환경
            ⓒSTOMP (Simple/Streaming Text Orientated Messaging Protocol):
                특징: 이름처럼 매우 간단한 텍스트 기반 프로토콜. HTTP와 유사한 형태로 동작하여 어떤 언어로든 클라이언트를 만들기 쉽습니다.
                주요 사용처: 웹소켓(WebSocket)을 통한 실시간 웹 애플리케이션, 간단한 메시징 연동

7. WebSocket 
    - websocket Handshake과정: 
    WebSocket 연결은 클라이언트와 서버가 "악수(Handshake)"를 하는 과정을 통해 수립됩니다. new WebSocket()을 호출하는 순간 이 과정이 시작됩니다.
    1단계: 클라이언트의 연결 요청 (HTTP Upgrade 요청)
        ⓐ new WebSocket(...) 실행: 클라이언트(브라우저)에서 코드가 실행되면, 단순한 TCP 연결이 아닌 특별한 HTTP GET 요청을 서버로 보냅니다.
        ⓑ 요청 헤더: 이 HTTP 요청의 헤더(Header)에는 다음과 같은 중요한 정보가 담겨 있습니다.
                Connection: Upgrade: "현재 이 HTTP 연결을 다른 프로토콜로 바꾸고 싶습니다."
                Upgrade: websocket: "그 다른 프로토콜은 'websocket' 입니다."
                Sec-WebSocket-Key: 보안 키. 서버가 정말 WebSocket을 지원하는지 확인하기 위한 암호화된 값입니다.
    2단계: 서버의 응답 및 연결 수립
        ⓒ 요청 수신: const server = createServer(...) 로 생성된 Node.js 서버가 이 특별한 HTTP 요청을 받습니다.
        ⓓ WebSocket 서버로 전달: const wss = new WebSocketServer({server}) 이 라인 덕분에, 일반 HTTP 요청이 아닌 "Upgrade" 요청은 wss (WebSocket 서버 인스턴스)가 처리하게 됩니다.
        ⓔ 핸드셰이크 응답: wss는 요청 헤더를 분석하고, WebSocket 연결을 수락할 준비가 되면 응답을 보냅니다.
        ⓕ 상태 코드 101 Switching Protocols: "알겠습니다. 지금부터 프로토콜을 전환합니다." 라는 의미의 응답입니다.
        ⓖ 응답 헤더: 이 응답에도 Connection: Upgrade, Upgrade: websocket 과 같은 헤더와 클라이언트가 보낸 Sec-WebSocket-Key를 이용해 만든 Sec-WebSocket-Accept 키를 함께 보내줍니다. 이는 "나도 WebSocket을 이해하고 당신의 요청에 동의합니다"라는 증표가 됩니다.
        ⓗ 연결 완료: 클라이언트가 101 응답을 받으면, 이제 이 통로는 일반적인 단방향 HTTP 통신이 아닌, 실시간으로 데이터를 주고받을 수 있는 양방향 WebSocket 통신으로 전환됩니다. 이 순간 wss.on('connection', ...) 이벤트가 서버에서 발생하고, 클라이언트에서는 ws.onopen 이벤트가 발생하며 연결이 성공적으로 수립됩니다.

    - 코드짜며 겪은 문제점: 
        ⓐ websocket프로토콜 하드코딩. 
            - const ws = new WebSocket('ws://' + window.document.location.host)은 로컬 개발환경에선 http -> ws로 업그레이드 가능함
            BUT 현재처럼 cloud Workstation에선 https로 서비스 되기에, 안전한 페이지가 ws라는 안전하지않은 페이지로 연결하는 것에 대해 mixed content 오류 (보안정책위반)냄. 
            - const wsProtocol = window.location.protocol === 'https:' ? 'wss' : 'ws';
              const ws = new WebSocket(`${wsProtocol}://${window.document.location.host}`);
              다음처럼 동적 프로토콜 방식으로, https면 wss로 설정해줌.

HTTP의 한계와 실시간 웹의 역사:

Polling: 클라이언트가 주기적으로 서버에 "새 소식 없어?"라고 묻는 방식. 비효율적이고 지연 시간이 발생.
Long-Polling: 클라이언트가 물어보면 서버가 새 소식이 생길 때까지 응답을 "대기"시키는 방식. Polling보다는 낫지만 여전히 연결-종료 오버헤드가 발생.
Server-Sent Events (SSE): 서버에서 클라이언트로의 단방향 통신. 서버가 클라이언트에게 "새 소식이야!"라고 계속 보내줄 수 있음. (WebSocket과 비교해서 차이점 이해하기)
왜 WebSocket인가? 위 기술들과 비교하여 WebSocket이 제공하는 **"완전한 양방향성"**과 **"낮은 오버헤드"**의 가치를 명확히 이해합니다.
WebSocket 프로토콜 명세 (RFC 6455) 파헤치기:

핸드셰이크(Handshake) 심층 분석:
이전 답변에서 설명한 Upgrade 요청 헤더를 넘어, Sec-WebSocket-Key가 어떻게 생성되고 서버가 이를 이용해 Sec-WebSocket-Accept를 만들어 응답하는지 직접 계산해봅니다. (Base64 인코딩, SHA-1 해싱 과정) 이것은 서버가 정말 WebSocket을 지원하는지 확인하는 핵심 과정입니다.
데이터 프레이밍(Data Framing):
핸드셰이크 이후 데이터가 어떻게 조각(Frame)나서 전송되는지 이해하는 것이 딥다이브의 핵심입니다.
Opcode: 이 프레임이 텍스트인지, 바이너리인지, 연결 종료(close) 신호인지, 아니면 ping/pong 인지 구분하는 식별자.
FIN bit: 메시지가 여러 프레임으로 분할되어 올 때, 이것이 마지막 프레임인지 알려주는 플래그. (메시지 조각화 및 재조립)
Masking: 클라이언트가 서버로 보내는 모든 프레임은 반드시 마스킹(XOR 연산으로 암호화)되어야 합니다. 이것이 왜 필요한지(프록시 캐시 오염 방지) 이해합니다.
제어 프레임 (Control Frames):
Close: 연결을 정상적으로 종료하는 방법.
Ping / Pong: 연결이 살아있는지 확인하는 하트비트(Heartbeat) 메커니즘.
이론을 바탕으로 직접 코드를 작성하며 개념을 체화합니다.

저수준(Low-level) 라이브러리 사용:

Node.js ws 라이브러리: Socket.IO 같은 고수준 라이브러리 대신 ws를 사용하여 WebSocket 서버를 직접 구축합니다. 이를 통해 핸드셰이크 과정, 클라이언트 관리, 메시지 브로드캐스팅을 직접 제어하며 프로토콜의 동작을 더 가까이서 느낄 수 있습니다.
프레임 데이터 직접 보기: ws 라이브러리에서 raw 버퍼 데이터를 출력해보며 Opcode나 Payload가 어떻게 생겼는지 눈으로 확인합니다.
바닐라 JS 클라이언트: 프레임워크 없이 순수 자바스크립트로 new WebSocket()을 사용하여 클라이언트의 네 가지 핵심 이벤트(onopen, onmessage, onclose, onerror)와 send() 메소드를 능숙하게 다룹니다.
데이터 직렬화(Serialization):

JSON을 사용한 텍스트 데이터 전송.
ArrayBuffer나 Blob을 사용한 바이너리 데이터 전송. (이미지, 오디오, 게임 데이터 등 고성능이 필요할 때)
Protocol Buffers (protobuf) 같은 스키마 기반 직렬화 라이브러리를 WebSocket과 함께 사용하는 방법을 학습하여 타입 안정성과 효율을 높입니다.
단순한 채팅앱을 넘어, 실제 서비스에서 마주할 문제들을 해결하는 방법을 배웁니다.

확장성 (Scalability):

수평 확장(Horizontal Scaling)의 함정: 사용자가 늘어나 서버를 여러 대로 늘렸을 때, A 서버에 접속한 유저에게 B 서버에서 발생한 이벤트를 어떻게 전달할까요?
백플레인(Backplane) 도입: Redis의 Pub/Sub 기능이나 RabbitMQ, NATS 같은 메시지 브로커를 사용하여 여러 서버 인스턴스 간에 메시지를 중계하는 아키텍처를 설계하고 구현합니다. 이것이 WebSocket 확장성의 핵심입니다.
보안 (Security):

WSS (Secure WebSocket): https:// 환경에서는 wss://를 사용하는 것이 필수임을 다시 한번 상기하고, Nginx나 다른 리버스 프록시에서 TLS 인증서를 설정하여 WSS를 활성화하는 방법을 배웁니다.
인증/인가(Authentication/Authorization):
WebSocket은 어떻게 사용자를 인증할까요? 핸드셰이크 과정이 유일한 기회입니다. HTTP Upgrade 요청 시 전달되는 쿠키나 쿼리 스트링의 JWT(JSON Web Token)를 검증하여 인가된 사용자인지 확인하고, 아니라면 연결을 거부하는 로직을 구현합니다.
안정성과 성능:

리버스 프록시 설정: Nginx, HAProxy, AWS ALB 등에서 WebSocket Upgrade 요청을 올바르게 백엔드 서버로 전달하기 위한 헤더 설정(proxy_set_header Upgrade $http_upgrade 등)을 마스터합니다.
하트비트와 재연결: Ping/Pong 프레임을 이용해 좀비 커넥션을 주기적으로 정리하는 하트비트 로직을 서버와 클라이언트에 모두 구현합니다. 클라이언트 측에서는 연결이 끊겼을 때 자동으로 재연결을 시도하는 로직(예: Exponential Backoff)을 구현합니다.
서브 프로토콜 (Sub-protocols): Sec-WebSocket-Protocol 헤더를 이용해 클라이언트와 서버가 특정 버전의 메시징 규약을 협상하는 방법을 학습하여, API처럼 WebSocket 통신을 버전 관리합니다.
위에서 배운 모든 지식을 종합하여 복잡한 애플리케이션을 만들어봅니다.

실시간 협업 도구 (e.g., Google Docs): 여러 사용자가 동시에 문서를 편집할 때 발생하는 충돌을 어떻게 해결할까요? CRDTs(Conflict-free Replicated Data Types) 또는 OT(Operational Transformation) 같은 알고리즘을 학습하여 적용해봅니다.
간단한 멀티플레이어 게임: 플레이어의 위치, 액션 등을 실시간으로 동기화하는 웹 게임을 만듭니다. 이 과정에서 바이너리 데이터 처리의 이점을 체감할 수 있습니다.
실시간 모니터링 대시보드: 서버의 로그나 성능 지표를 실시간으로 차트에 그려주는 대시보드를 구축합니다.

기존 HTTP: 
http.createServer로 만든 서버는 엄격한 "요청-응답" 모델을 따름. 
-> 클라이언트가 '항상' 먼저 요청해야함. (fetch 등)
-> 서버는 그 요청에 대해 딱 한 번만 응답(Response)할 수 있음. 서버는 res.end()나 res.send() (Express.js의 경우)를 호출하여 응답을 보내고 나면, 그 특정 통신은 그걸로 완전히 끝납니다.
-> 서버는 먼저 말 걸수 없음! (클라이언트에게 새로 메시지 왔다고 알려주고 싶어도, 클라이언트로부터 들어오는 요청이 없다면 데이터를 보낼 방법자체가 없음)

요청/응답 모델인 이유?: 
    - HTTP는 "문서(Document)"를 가져오기 위해 설계된, 상태가 없는(Stateless) 프로토콜(상태가 없기에, 서버는 클라이언트에 대한 정보가 없어서 서버가 먼저 클라이언트에게 연락이 안됨 + 매 메시지마다 메타데이터(http헤더)를 포함해서 보내야 하기에 HTTP의 경우 오버헤드가 크다.)
    - HTTP는 서버가 클라이언트의 이전 요청을 기억하지 않는 것을 기본 원칙으로 함. (어떤 서버가 요청을하던, 상관없기에 수평 확장에 유리!)
        - 문서 가져오기 (Document Retrieval):
        초기 목적: HTTP(HyperText Transfer Protocol)의 원래 목적은 분산된 하이퍼텍스트 문서를 주고받는 것이었습니다. "이 페이지 줘" -> "여기 있어" 라는 단순 명료한 작업의 연속이었죠.
        HTTP/1.1의 Keep-Alive: 이전에는 요청마다 TCP 연결을 새로 맺고 끊는 비효율이 있었습니다. HTTP/1.1부터는 하나의 TCP 연결을 재사용(Keep-Alive)할 수 있게 되었지만, 이것은 프로토콜의 본질을 바꾼 것이 아닙니다. 여전히 그 재사용되는 연결 통로 위에서는 "요청이 먼저 오면 -> 응답을 보낸다"는 규칙이 엄격하게 지켜집니다.

WebSocket 이전의 보완 기술들: 
ⓐ polling: 클라이언트가 일정한 간격으로 (예: 매 2초마다) 서버에 계속해서 "새로운 소식 없어?" 라고 물어보는 방식 -> 대부분은 새 소식없다는 의미없는 빈 응답
ⓑ long-polling





8. redis
    - redis는 메모리 기반이지만, 영속적인 데이터보존이 가능! 
        ⓐ 메모리: 항상 휘발성. RAM(Random Access Memory)은 전력 공급이 끊기면 데이터가 모두 사라지는 휘발성. 
    - Redis는 인메모리(In-memory) 데이터베이스. -> 메모리에서 데이터가 사라지는걸 방지하기 위해 2가지 방식 제공 ! 
        ① RDB(redis Database): 
            - 스냅샷 방식
            - 특정 시점의 메모리 상태를 통째로 찍듯이 복사하여 디스크에 dump.rdb 파일로 저장함.  
            - 설정된 시점마다(15분 마다) 스냅샷 새성 
            - 장점: 하나의 파일로 저장되어 백업 및 복구 간편 + AOF 방식보다 파일 크기가 작음. 
            - 단점: 마지막 스냅샷 이후에 발생되는 데이터 변경 사항은 유실될 수 있음! 
        ② AOF(Append Only File):
            - 로그 기록 방식
            - Redis에 데이터를 변경하는 모든 쓰기/수정/삭제 명령어를 로그 파일(appendonly.aof)에 순서대로 기록
            - 이 실행될 때마다 즉시, 또는 1초마다 로그 파일에 기록하도록 설정할 수 있습니다. Redis가 재시작될 때 이 로그 파일을 처음부터 끝까지 다시 실행하여 데이터를 복원
            - 장점: 데이터 유실 가능성 매우 낮음 + 데이터 변경 이력이 모두 기록되어 안정성 높음 
            - 단점: 모든 명령어를 기록하여 RDB보다 파일 크기가 큼 + 복구 시 모든 명령어 재실행하기에, 데이터 양 많으면 RDB보다 복구 속도 느릴 수 있음. 
    - redis는 싱글스레드고, race condition 방지를 위해 atomic 지원. 
    - Node.js 애플리케이션들은 메모리나 내부 IPC를 공유하는 것이 아니라, 라이브러리(amqplib, redis)를 통해 각각 Redis 서버나 RabbitMQ 서버의 지정된 포트(Port)로 TCP 연결을 맺고, 정해진 프로토콜에 맞춰 메시지를 주고받는 클라이언트-서버 모델

10. Message Broker vs. Brokerless
    - Messaging 시스템은 메시지를 중개하는 중앙 서버(Broker)의 유무에 따라 크게 두 가지 방식으로 나뉩니다. 
    
    ① Message Broker (중개인 모델)
        - 대표 주자: RabbitMQ, Apache Kafka, ActiveMQ
        - 아키텍처: 중앙에 '브로커'라는 서버가 존재하며, 모든 메시지는 이 브로커를 거쳐 전달됩니다.
        - 비유: 우체국 시스템. 보내는 사람(Producer)은 우체국(Broker)에 편지를 맡기기만 하면, 우체국이 받는 사람(Consumer)에게 배달을 책임집니다.
        - 장점:
            - 완벽한 분리(Decoupling): Producer와 Consumer는 서로를 전혀 몰라도 되며, 심지어 동시에 온라인 상태일 필요도 없습니다. Broker가 메시지를 안전하게 보관해줍니다. (line 75, 78 참고)
            - 데이터 보장(Durability): Broker가 메시지를 저장하므로 안정적인 전달을 보장합니다.
            - 관리 용이성: 모든 메https://studio.firebase.google.com/u/1/node-design-system-81022038시지 흐름이 중앙 브로커를 통하므로 모니터링과 관리가 쉽습니다.
        - 단점:
            - 성능/지연: 모든 메시지가 브로커를 거치므로 Brokerless 방식보다 느릴 수 있습니다.
            - 단일 장애점(SPOF): 브로커에 장애가 발생하면 전체 시스템이 마비될 수 있습니다. (이를 막기 위해 클러스터링 구성이 필요하며 운영 복잡도가 증가합니다.)
            
    ② Brokerless (P2P 모델)
        - 대표 주자: ZeroMQ (ØMQ)
        - 아키텍처: 중앙 서버 없이, 각 애플리케이션(노드)이 라이브러리를 통해 직접 P2P(Peer-to-Peer)로 연결됩니다.
        - 비유: 직통 전화. A와 B가 교환원(Broker) 없이 직접 통화하는 것과 같습니다.
        - 장점:
            - 초고속 & 저지연: 중간 단계를 거치지 않으므로 메시지 전달 속도가 매우 빠릅니다.
            - 가벼움: 별도의 서버 관리가 필요 없고, 애플리케이션에 라이브러리만 포함하면 됩니다.
            - 유연성: 개발자가 원하는 대로 복잡한 통신 네트워크를 자유롭게 구성할 수 있습니다.
        - 단점:
            - 약한 데이터 보장: 메시지를 받는 Consumer가 오프라인 상태면 메시지가 유실될 수 있습니다. (이를 방지하려면 개발자가 직접 재전송 로직 등을 구현해야 합니다.)
            - 상대적 결합: 일반적으로 메시지를 주고받으려면 Producer와 Consumer가 동시에 온라인 상태여야 합니다. (line 73 참고)



    - MOM(Message Oriented Middleware): 메세지 지향 미들웨어 
        장점: 
            클라이언트 시스템 사이에서 메시지 통신을 중간에서 관리하여 종속성, 결속성 낮춤. 
            안정성 - 메시지 db에 기록하는 등 백업 가능. (수신서버거 꺼져있어도 메시지는 미들웨어에 보관됨)
            확장성 - 새로운 서비스가 추가되어도 미들웨어에만 연결되면 됨. 
        단점: 
            메시지 전체 관리하는 시스템이 따로 필요 -> 도입비용, 운용 비용 
            시스템 구조가 복잡해짐
        MOM은 설계적 방향성을 제시하는것 뿐.
        직접적 구현: AMQP (미들웨어 브로커 간 메시지 교환을 위한 프로토콜), zeroMQ, RabbitMQ, Kafka 등.. 
    - 사용하는 이유: 
        송신자가 수신자에게 그냥 보내는건 안되나? -> 송신자가 많이 보내면 수신자 과부하>? -> 이건 브로커도 마찬가진가? -> 브로커가 고성능 서버면 차라리 수신자도 고성능으로 해서 복잡성 낮추면 안되나?? 
        이렇게 생각할수있음. BUT decoupling !!! 
    - 메시지를 매개로 하여 비동기적으로 데이터를 주고받는 소프트웨어". -> 브로커가 있느냐 없느냐보다는 "애플리케이션과 네트워크 프로토콜 사이에 추상화 계층이 있는가"가 더 중요


11. ZeroMQ
    - message brokerless ! -> 브로커 추가한다는건 장애지점, 관리비용이 늘어나는것! 
    - raw socket programming의 단점과 zeromq의 극복
    - ZeroMQ의 소켓은 저수준 TCP 소켓이 아닌, 특정 통신 패턴(PUB/SUB, PUSH/PULL 등)이 내장된 고수준 객체입니다. 연결 관리, 재연결 시도 등을 자동으로 처리합니다.
    - bind: 소켓이 특정 주소(예: tcp://*:5000)를 점유하고, 다른 노드로부터의 연결 요청을 수신 대기합니다. 네트워크에서 고정된 엔드포인트 역할을 합니다.

    
    1. 포어그라운드 vs 백그라운드 (Blocking vs Non-blocking)
        일반 소켓 프로그래밍에서는 recv()나 accept() 시 흐름이 멈추는(Blocking) 문제를 해결하기 위해 멀티스레딩이나 Select/Poll/Epoll 같은 복잡한 I/O 멀티플렉싱을 직접 구현해야 합니다.
        ZeroMQ의 해결: 모든 통신이 내부 I/O 스레드에서 비동기로 처리됩니다. 사용자 코드(애플리케이션 스레드)는 메시지를 큐에 던지기만 하고 즉시 다음 작업을 수행할 수 있어, 통신 모델 설계가 훨씬 단순해집니다.

    2. 존재 책임과 Reconnect 주체 문제
        클라이언트가 서버보다 먼저 켜지거나, 서버가 재시작될 때 소켓은 보통 Connection Refused 에러를 뱉고 종료됩니다. 누가 먼저 접속을 시도할지(Retry 로직)를 정하는 것도 골치 아픈 일입니다.
        ZeroMQ의 해결: "신뢰성 있는 재연결(Automatic Reconnect)"을 라이브러리 레벨에서 보장합니다. 어떤 노드가 먼저 켜지든 상관없으며, 연결이 끊기면 백그라운드에서 자동으로 재시도합니다. 개발자는 상대방의 상태를 체크하는 '연결 관리자' 역할에서 해방됩니다. (상대 오프라인일 때 send해도 에러 없음. 메시지는 내부 큐로! )

    3. 메시지 프레이밍 (Data Framing)
        TCP는 Byte Stream 방식입니다. 100바이트를 보냈어도 받는 쪽에서는 네트워크 상황에 따라 50바이트, 50바이트씩 나눠서 받을 수 있습니다. 비디오나 텍스트 같은 가변 데이터를 처리하려면 헤더에 길이를 적고 파싱하는 로직을 직접 짜야 합니다.
        ZeroMQ의 해결: "Message-based Transport"를 제공합니다. 보내는 쪽에서 한 덩어리로 보내면 받는 쪽에서도 반드시 그 한 덩어리(Atomic Message)로 받습니다. 데이터가 아무리 크거나 작아도 "경계(Boundary)"를 라이브러리가 지켜줍니다.
  
    4. 큐(Queue) 관리와 Overload 전략 (HWM)
        소켓 버퍼가 가득 차면 시스템은 패킷을 버리거나 송신측을 블로킹합니다. 이를 애플리케이션에서 제어하기는 매우 어렵습니다.
        ZeroMQ의 해결: HWM(High Water Mark) 옵션을 제공합니다. 큐가 꽉 찼을 때 메시지를 조용히 버릴지(Drop), 아니면 송신자를 대기시킬지(Block)를 설정 한 줄로 결정할 수 있습니다. 이는 시스템의 배압(Backpressure)을 조절하는 핵심 장치가 됩니다.

    - 기능

    - [중요] broker과 brokerless의 큰 차이!!!!! 
        ⓐ ZeroMQ
            1. 서버 A가 pubSocket.send(msg)로 메시지를 발행합니다.
            2. ZeroMQ의 PUB 소켓은 이 메시지를 자신을 제외한 모든 구독자(Subscriber)에게만 보냅니다. 즉, 서버 B와 서버 C는 메시지를 받지만, 서버 A의 subSocket은 이 메시지를 받지 못합니다.
            이것은 의도된 설계입니다. 불필요한 네트워크 피드백 루프를 방지하기 위함입니다.
            결과적으로, 메시지를 보낸 사람은 자신이 보낸 메시지를 되돌려 받을 수 없습니다.
        ⓑ Redis/AMQP
            1. 서버 A가 메시지를 Broker에 발행(Publish)합니다.
            2. Broker는 이 메시지를 모든 구독자에게 전파합니다. 여기서 "모든 구독자"에는 서버 A 자신도 포함됩니다.
            3. 따라서 서버 A는 sub 로직에서 자신이 보낸 메시지를 다시 돌려받고, 연결된 클라이언트들에게 broadcast합니다.
            4. 로직이 단순해집니다: "메시지 수신 -> 무조건 방송"

    1. JavaScript 계층: await pushSocket.bind('tcp://*:5000') 코드를 실행합니다.
    2. Node.js 바인딩 계층: zeromq 라이브러리가 이 JavaScript 호출을 C++ 함수 호출로 변환합니다.
    3. ZeroMQ 코어 계층 (C++):
        소켓 생성: OS(운영체제)에게 TCP 소켓을 만들어달라고 요청합니다. (socket() 시스템 콜) (OS는 socket() 시 커널 메모리 공간과 데이터 구조(상태, 버퍼 등)를 할당하고, 이 리소스에 접근할 수 있는 fd 줌. 해당 fd로 application이 통신 제어함.)
        주소 할당: 만들어진 소켓에 tcp://*:5000 주소를 할당(점유)합니다. (bind() 시스템 콜) (서버의 모든 IP 주소에 대해 5000port로 들어오는 TCP 연결은 아까 만든 소켓(fd)로 처리하겠다고 OS에 등록하는 것)
        연결 대기: 외부 연결을 받을 준비를 합니다. (listen() 시스템 콜) ( 대기 큐 생성하고, 실제 클라이언트 요청오면 요청을 대기큐에 넣음. )
        I/O 폴러(Poller) 등록: 이 소켓을 ZeroMQ의 백그라운드 I/O 스레드가 관리하는 I/O 감시 목록(epoll, kqueue 등)에 등록합니다. 이제부터 이 소켓으로 들어오는 모든 연결 요청은 I/O 스레드가 감지하게 됩니다.
        결과: pushSocket은 5000번 포트를 리스닝하며, 새로운 PULL 워커의 접속을 기다리는 '접수 창구'가 됩니다. 하지만 아직 실제 워커와 연결된 상태는 아닙니다.

    - 클라이언트에서 connect 할 때 
    1. JavaScript 계층: 워커 프로세스에서 await pullSocket.connect('tcp://<server_ip>:5000') 코드를 실행합니다.
    2. Node.js 바인딩 & 코어 계층:
        소켓 생성: 워커 측에서도 OS에게 TCP 소켓을 만들어달라고 요청합니다. (socket() 시스템 콜)
        서버에 연결: 이 소켓을 사용해 서버 주소(tcp://<server_ip>:5000)로 연결을 시도합니다. (connect() 시스템 콜) 이 과정에서 TCP 3-way-handshake가 일어납니다.
        연결 성공: 서버의 pushSocket이 연결을 수락하면, PUSH-PULL 간에 하나의 TCP 연결 파이프라인이 생성됩니다.
        I/O 폴러 등록: PUSH 측과 마찬가지로, 이 연결된 소켓 역시 양쪽(PUSH, PULL)의 I/O 스레드 감시 목록에 등록됩니다.
        결과: 서버의 pushSocket은 이제 자신에게 연결된 pullSocket의 목록을 내부적으로 유지하게 됩니다. (예: [worker_A_connection, worker_B_connection, ...])

    - PUSH/PULL과 bind, connect간 관계. 
        - 난 처음에 push 소켓에는 무조건 서버라 bind라고 생각했음. (이건 일반적인 웹에선 맞는 말)
        다만 log aggregator처럼 하나의 sink에서 데이터를 PULL 해야하는 상황이고 여러 transient node인 worker에서 PUSH를 하는경우엔, durable한 Node에 bind를 줘야함.
        즉 Push에도 conenct를 주고, pull에는 bind를 주는 경우도 생김! 

        - 방화벽 및 네트워크 보안 문제 (NAT 호환성)
        실무에서 분산 시스템을 구축할 때 가장 큰 걸림돌 중 하나는 방화벽(Firewall)과 공유기(NAT)입니다.
        보통 회사나 집에서 쓰는 컴퓨터(Worker)는 외부에서 함부로 접속할 수 없도록 방화벽이 쳐져 있거나 가상 IP를 씁니다. 즉, 외부에서 이 Worker 컴퓨터를 향해 connect를 찌르는 것은 보안상 거의 불가능합니다. (포트 포워딩 같은 복잡한 설정이 필요합니다.)
        반면, 클라우드에 올려둔 메인 서버(Ventilator)는 공인 IP를 가지고 있고 포트가 열려 있기 때문에, 내 컴퓨터(Worker)가 서버를 향해 나가는 연결(Outbound connect)을 시도하는 것은 방화벽에 걸리지 않고 아주 자유롭습니다.
        따라서 안정적인 서버에 bind를 주고, 사설 네트워크에 있는 작업자들에게 connect를 주는 것이 네트워크 설정상 훨씬 현실적이고 안전합니다.

        - IP 주소를 몰라도 됨 (서비스 디스커버리 최소화)
        Worker가 bind할 때: 메인 서버는 모든 Worker의 IP 주소를 실시간으로 다 기억하고 관리해야 합니다. (Worker가 갑자기 죽으면 그 IP를 목록에서 지워야 함)
        서버가 bind할 때: Worker들은 메인 서버의 IP 딱 하나만 기억하면 됩니다. 수많은 Worker의 주소를 관리하는 복잡한 시스템(Service Discovery)을 구축할 필요가 없어집니다.

13. socket
    - 소켓은 소프트웨어로 작성된 통신 접속점이라고 할 수 있는데 네트웍 응용 프로그램은 소켓을 통하여 통신망으로 데이터를 송수신하게 된다.
    - 소켓번호: 
        ▶UNIX에서 파일을 새로 열면(open) int 타입의 정수를 리턴하는데 이와같이 open문이 리턴한 정수를 파일기술자(file descriptor)라고 하며 프로그램에서 open된 파일을 액세스할 때 이 파일기술자를 사용하게 된다.
        ▶ 파일기술자(fd)는 기술자 테이블(descriptor table)의 index 번호. 기술자 테이블이란 현재 open되어 있는 파일의 각종 정보를 포함하고 있는 구조체를 가리키는 포인터들로 구성된 테이블
        ▶ 프로그램에서 소켓을 개설하면 파일기술자와 똑같은 기능을 하는 소켓기술자(socket descriptor)가 리턴
        ▶ 응용 프로그램에서 이 소켓을 통하여 목적지 호스트와 연결을 요구하거나 패킷을 송수신할 때 해당 소켓기술자를 사용
        ▶ UNIX에서는 파일기술자와 소켓기술자가 같은 기술자 테이블의 index가 된다. 즉, 파일과 소켓이 기술자 테이블을 공유  -> fd와 socket discriptor은 중복될 수 없음.

432.          - 이 패킷은 인터넷을 거쳐 서버 컴퓨터의 네트워크 카드에 도착합니다.

437.          - OS는 이전에 `server.listen(8080)`을 호출한 우리의 Node.js 애플리케이션을 찾아냅니다.
438.     
439.       3. **연결 수립 및 새 소켓 생성 (`accept`)**
440.          - OS는 클라이언트와 3-way-handshake를 완료하여 TCP 연결을 확립합니다.
441.          - **(핵심)** 이제 이 클라이언트와의 **'전용 통신 회선'**을 위해, OS는 **새로운 소켓**을 생성합니다. 기존의 `listen`하던 소켓은 다른 새로운 손님을 계속 기다립니다.
442.     
443.       4. **소켓 디스크립터(Socket Descriptor): 내부 관리용 핸들**
444.          - OS는 방금 생성한 **새로운 '전용 소켓'**에 대한 **내부 관리용 번호표(정수 값)**를 발급합니다. 이것이 바로 **소켓 디스크립터**입니다.
445.          - OS는 이 소켓 디스크립터를 우리 Node.js 애플리케이션에게 전달해 줍니다.
446.          - **중요:** 소켓 디스크립터는 '통신 채널' 그 자체가 아니라, 애플리케이션이 OS에게 "방금 연결된 그 클라이언트와 통신하고 싶어요"라고 말할 때 사용하는 **'핸들(손잡이)' 또는 '식별표'**입니다.
439.     
440.       5. **데이터 통신**
441.          - 이제 애플리케이션은 OS가 전달해준 이 소켓 디스크립터를 사용하여 데이터를 읽거나(`read`) 씁니다(`write`).
442.          - 예: "소켓 디스크립터 7번으로 이 데이터를 보내줘!" 라고 OS에 요청 &rarr; OS가 실제 네트워크 통신을 처리.
443.          - 클라이언트는 서버의 소켓 디스크립터가 몇 번인지 전혀 알지 못하며, 알 필요도 없습니다. 이것은 순전히 서버 애플리케이션과 OS 사이의 약속입니다.



   14. AMQP 
        - MOM (메시지 지향 미들웨어)를 위한, 개방형 표준 프로토콜. 
        - publisher -> broker -> consumer로 큰 흐름이 있고, broker에 AMQP의 3가지 요소가 있음. 
            broker: publisher과 consumer 사이에서 메시지를 관리하고 전달하는 중앙 서버
                ① exchange: publisher로 받은 메시지를 어떤 큐에 보낼지 결정하는 라우팅 역할 
                    - 방식 3가지 + α
                        ⓐ Direct Exchange: 메시지의 라우팅 키(routing key)와 큐의 바인딩 키(binding key)가 정확히 일치하는 큐로 메시지를 전송. (1:1 통신에 적합)
                        ⓑ Fanout Exchange: 라우팅 키를 무시하고, 자신에게 바인딩된 모든 큐에 메시지를 브로드캐스팅(전체 전송). (전체 공지, 1:N 통신에 적합)
                        ⓒ Topic Exchange: 라우팅 키에 패턴 매칭을 사용. `*`(하나의 단어), `#`(0개 이상의 단어) 와일드카드를 이용해 복잡하고 유연한 라우팅 규칙을 만들 수 있음. (예: `logs.critical.*`)

                ② Queue (큐): Consumer가 메시지를 가져가기 전까지 안전하게 보관하는 저장소.
                    - 생성 시 주요 속성들:
                        ⓐ durable: `true`일 경우, 브로커가 재시작되어도 큐의 정의가 사라지지 않고 유지됨 (디스크에 저장). 메시지 자체의 영속성은 별개.
                        ⓑ exclusive: `true`일 경우, 큐를 선언한 연결(connection)에서만 접근 가능하며, 해당 연결이 끊어지면 큐가 자동으로 삭제됨.
                        ⓒ auto-delete: `true`일 경우, 마지막 소비자가 구독을 취소하면 큐가 자동으로 삭제됨.

                ③ Binding (바인딩): Exchange와 Queue를 연결하는 규칙
                    - "이 Exchange는 이 routing key 패턴을 가진 메시지를 저 Queue로 보내라" 라고 정의함.



        - 메시지 전달 실패(네트워크 오류 등) 방지하기 위해 
        -> message acknowledgements사용 : when a message is delivered to a consumer the consumer notifies the broker, either automatically or as soon as the application developer chooses to do so. 
        When message acknowledgements are in use, a broker will only completely remove a message from a queue when it receives a notification for that message (or group of messages).

        - routing algorithm used depends on the exchange type and rules called bindings
        - 주요 메서드 (amqplib 기준)
                        1. 연결 및 채널 설정 (Setup)
                            - `amqp.connect(url)`: RabbitMQ 서버와 TCP 연결 생성. 연결 객체 담은 promise 반환
                            - `connection.createChannel()`: 연결 내에 독립적인 통신 회선(채널) 생성. 대부분의 작업은 채널을 통해 이루어짐. 채널(Channel) 객체를 담은 Promise 반환

                        2. 구조 선언 (Declare) - 없으면 만들고, 있으면 넘어감! 
                            - `channel.assertExchange(name, type, options)`: Exchange를 선언(생성). // type (string): Exchange의 타입 ('direct', 'fanout', 'topic'). options (object): { durable: true } 설정 시 브로커가 재시작되어도 Exchange가 유지 
                            - `channel.assertQueue(name, options)`: Queue를 선언(생성).
                            - `channel.bindQueue(queue, source, pattern)`: Exchange와 Queue를 바인딩(연결).

                        3. 메시지 발행 (Publish)
                            - `channel.publish(exchange, routingKey, content, options)`: Exchange에 메시지를 발행.
                                - `options`: `{ persistent: true }` 설정 시 메시지 영속성 부여.

                        4. 메시지 소비 (Consume)
                            - `channel.consume(queue, onMessage, options)`: 큐를 구독하여 메시지를 비동기적으로 수신.
                                - `options`: `{ noAck: false }`가 기본이며, 수동 확인 응답을 의미 (권장).
                            - `channel.ack(message)`: 메시지 처리 성공 확인 응답. 큐에서 메시지를 안전하게 제거.
                            - `channel.nack(message, all, requeue)`: 메시지 처리 실패 응답. 큐에 다시 넣거나 폐기하도록 제어.

            5. 수신 (Consume): 8080 서버와 8081 서버는 각각 자신의 큐에 메시지가 도착했음을 channel.consume을 통해 감지함.

            6. 처리: 각 서버는 수신한 메시지를 자신의 서버에 연결된 모든 클라이언트에게 broadcast 함.

                                     즉, Subscriber가 Publisher의 주소를 알아야 하는 의존성이 있습니다.
            ⓑ RabbitMQ (Broker 모델): Publisher와 Subscriber는 서로의 존재나 주소를 전혀 알 필요가 없습니다.
                                      그들은 오직 중앙의 브로커(RabbitMQ 서버) 주소만 알면 됩니다. 모든 통신은 브로커를 통해 이루어집니다.

        ### [심화] RabbitMQ 공유 모델과 Chat App 상세 워크플로우

        핵심 개념: Exchange와 Queue는 각 서비스의 메모리나 프로세스 내에 존재하는 것이 아닙니다. 이들은 **독립된 RabbitMQ 브로커(서버) 프로세스 안에 존재하는 객체**이며, 모든 서비스는 네트워크를 통해 이 '중앙 브로커'에 접속하여 공유합니다.

        ---

        #### 1. 왜 모든 서비스 코드에 Exchange/Queue 설정(Assert) 코드가 있나요?

        각 서비스(Chat Service, History Service 등) 코드에서 `channel.assertExchange('chat', 'fanout')` 같은 코드를 실행하는 이유는 **"멱등성(Idempotency)"**을 보장하기 위함입니다.

        - **선언적 의미**: "내가 지금부터 사용하려는 `chat`이라는 이름의 `fanout` Exchange가 브로커에 확실히 존재하게 해달라"는 선언입니다.
        - **동작 방식**:
            1. 클라이언트 라이브러리가 브로커에 "이 이름의 Exchange가 있니?"라고 확인합니다.
            2. **있으면**: 아무것도 하지 않고 그대로 사용합니다.
            3. **없으면**: 해당 이름과 타입으로 새로 생성합니다.
        - **공유의 원리**: Chat Service가 `chat` Exchange를 선언하고, History Service도 똑같이 `chat` Exchange를 선언하면, 두 서비스는 결국 RabbitMQ 서버 안에 **이미 생성되었거나 새로 생성된 단 하나의 `chat` Exchange**를 함께 바라보게 됩니다. 서비스가 몇 개가 되든 마찬가지입니다.

        ---

        #### 2. 아키텍처 구조: 내부 공유가 아닌 외부 공유

        프로세스 간 통신(IPC)이나 메모리 공유와는 전혀 다른 모델입니다.

        | 구분             | 서비스 A (Chat Service)        | 서비스 B (History Service)     | RabbitMQ (Broker)                      |
        | ---------------- | ------------------------------ | ------------------------------ | -------------------------------------- |
        | **실행 주체**    | 독립된 Node.js 프로세스        | 독립된 Node.js 프로세스        | 독립된 서버/컨테이너 (외부 프로세스)   |
        | **역할**         | 메시지를 발행(Publish)         | 메시지를 소비(Consume)         | Exchange/Queue 관리 및 메시지 라우팅   |
        | **연결 방식**    | `amqp://localhost` 접속 (TCP)  | `amqp://localhost` 접속 (TCP)  | 외부로부터 TCP 연결 수락             |
        | **인식 범위**    | History Service의 존재를 모름  | Chat Service의 존재를 모름     | 두 서비스의 연결을 모두 인지하고 관리  |

        ---

        #### 3. Chat App 상세 통신 흐름 (네트워크 통신 기준)

        **[시나리오]** Chat Service는 메시지를 받아 전파하고, History Service는 모든 메시지를 받아 데이터베이스에 저장합니다.

        **Phase 1: 초기 설정 (각 서비스 시작 시)**

        1.  **History Service 시작**:
            a. RabbitMQ 서버에 네트워크 연결(`amqp.connect`).
            b. 채널 생성.
            c. `channel.assertExchange('chat', 'fanout')`: 브로커에 `chat` Exchange가 있는지 확인/생성.
            d. `channel.assertQueue('history-queue', { durable: true })`: 메시지를 안전하게 저장할 `history-queue` 생성. `durable` 옵션으로 브로커가 재시작돼도 큐가 유지되도록 함.
            e. `channel.bindQueue('history-queue', 'chat', '')`: `chat` Exchange에 들어온 모든 메시지를 `history-queue`로 보내달라고 규칙(바인딩) 설정.
            f. `channel.consume('history-queue', ...)`: `history-queue`에 메시지가 들어오는지 리스닝 시작.

        2.  **Chat Service 시작**:
            a. RabbitMQ 서버에 네트워크 연결.
            b. 채널 생성.
            c. `channel.assertExchange('chat', 'fanout')`: 브로커에 `chat` Exchange가 있는지 확인. (History Service가 이미 만들었으므로 아무 일도 일어나지 않음)

        **Phase 2: 메시지 발행 및 소비**

        3.  **이벤트 발생**: 사용자가 웹소켓 클라이언트를 통해 Chat Service에 "Hello World" 메시지를 전송.

        4.  **메시지 발행 (Publish)**:
            - **Chat Service**: 수신한 "Hello World" 메시지를 `channel.publish('chat', '', Buffer.from('Hello World'))`를 통해 RabbitMQ 브로커의 `chat` Exchange로 전송 (네트워크 요청).

        5.  **메시지 라우팅 (Routing)**:
            - **RabbitMQ Broker**: `chat` Exchange에 메시지가 도착.
            - Exchange 타입이 `fanout`이므로, 자신에게 바인딩된 모든 큐를 찾음 (현재 `history-queue`).
            - "Hello World" 메시지를 복사하여 `history-queue`에 넣음.

        6.  **메시지 수신 (Consume)**:
            - **History Service**: `consume`을 통해 대기하던 중 `history-queue`에 새 메시지가 도착했음을 감지하고 메시지를 가져옴.

        7.  **처리 및 확인 (Process & Ack)**:
            - **History Service**: 가져온 "Hello World" 메시지를 자신의 DB(`LevelDB`)에 저장.
            - 저장이 성공적으로 완료되면, `channel.ack(msg)`를 호출하여 브로커에게 "이 메시지 처리 완료했어"라고 알림 (네트워크 응답).
            - **RabbitMQ Broker**: `ack` 신호를 받고 `history-queue`에서 해당 메시지를 완전히 삭제. (만약 History Service가 처리 중 죽으면, `ack`를 못 받으므로 메시지는 큐에 남아 다른 컨슈머가 처리하거나 재시작 후 다시 처리 가능)

        ---

        #### 4. 왜 다이어그램에서는 공유되는 것처럼 보일까?

        다이어그램에서 Exchange가 하나로 그려지는 이유는 **논리적 실체(Logical Entity)가 실제로 하나**이기 때문입니다.

        -   **각 서비스의 코드**: "우체국(RabbitMQ)에 가서 '채팅' 창구(Exchange)를 이용하겠다"는 **지침서**일 뿐입니다.
        -   **실제 Exchange**: 우체국 안에 실제로 만들어진 **단 하나의 '채팅' 창구**입니다.

        따라서 여러 독립된 서비스(프로세스)들이 각자의 코드에서 동일한 이름의 Exchange를 선언하더라도, 그들은 결국 네트워크 너머에 있는 **하나의 공유 통로**를 통해 메시지를 주고받게 되는 것입니다.



15. UUID VS ULID
    - UUID(Universally Unique Identifier, 범용 고유 식별자)는 컴퓨터 시스템에서 정보를 고유하게 식별하기 위한 128비트 표준 식별자
     16진수 32개와 하이픈(-)으로 구성된 36자리의 문자열 형태(8-4-4-4-12 패턴)로, 중앙 집중식 등록 없이도 전 세계적으로 중복될 확률이 거의 없어 데이터베이스의 Primary Key, 세션 ID 등 분산 환경에서 많이 사용
    - ULID:  ULID는 시간 순서대로 정렬됩니다. UUID와 달리 ULID가 타임스탬프를 포함.  26자의 대소문자 구분이 가능한 Base32 문자열로 표현


16. MQ vs Stream
    ① 메시지 큐 (Message Queue)
        - 철학: 처리해야 할 "작업" 목록.
        - 데이터 보존: 소비자가 메시지를 성공적으로 처리하면 큐에서 "삭제됨". (소멸성)
        - 소비 모델: 하나의 메시지는 하나의 소비자에게만 전달되어 처리됨. (작업 분배)
        - 대표 기술: RabbitMQ, Amazon SQS

    ② 스트림 (Stream)
        - 철학: 발생한 모든 "사건"의 영구적인 기록부(Log).
        - 데이터 보존: 소비자가 메시지를 읽어도 "삭제되지 않음". (영속성)
        - 소비 모델: 여러 소비자가 각자 독립적으로 동일한 메시지를 읽을 수 있음. (데이터 공유, 재처리 가능)
        - 대표 기술: Apache Kafka, Redis Streams
        - 
    - 방식 차이: 
        메시징 큐는 생산자가 직접 소비자의 큐로 메시지를 푸시(push) 하는 방식
        그래서 만약 하나의 메시지를 두 개 서비스에 보내야 한다면, 생산자가 각각 따로 "두 개의 메시지"를 만들어서 각각의 큐에 넣어야 한다.

        그러나, 스트림의 경우에는, 생산자가 스트림 저장소에 메시지를 한 번만 넣으면, 여러 소비자가 같은 메시지를 가져가서 읽을 수 있다.(Pull)
        즉, 메시지를 복제해서 따로 저장하지 않아도 된다.

    - 새로운 소비자 추가 시: 
        메시징 큐는 소비자가 중간에 들어오면, 그 시점 이후의 메시지부터만 조회 가능
        이벤트 스트림은 저장소에 남아 있는 과거 데이터까지 조회 가능. 나중에 들어온 소비자라도 이전 기록을 확인 가능-> 히스토리 열람 가능
        
17. Redis Stream 
    ① XADD: 스트림에 메시지 추가
        - 역할: 스트림의 끝에 새로운 메시지(엔트리)를 추가함.
        - 사용법: `redis.xadd(key, '*', field1, value1, ...)`
        - 설명: `key` 스트림에 `field-value` 쌍으로 구성된 메시지를 추가. ID로 `*`를 주면 Redis가 자동으로 타임스탬프 기반 ID를 생성.

    ② XRANGE / XREVRANGE: 스트림의 메시지 범위 조회
        - 역할: 스트림의 특정 범위에 있는 메시지들을 조회 (단순 읽기, 소비 아님).
        - 사용법: `redis.xrange(key, start, end)`
        - 설명: `start` ID부터 `end` ID까지의 메시지를 조회. `-`는 가장 오래된 메시지, `+`는 가장 최신 메시지를 의미. `XREVRANGE`는 역순 조회.

    ③ XREADGROUP: 소비자 그룹으로 메시지 읽기 (핵심 기능)
        - 역할: 소비자 그룹에 속한 소비자로서, 아직 처리되지 않은 메시지를 가져와 처리.
        - 사용법: `redis.xreadgroup('GROUP', group, consumer, 'STREAMS', key, '>')`
        - 설명: `group`에 속한 `consumer`가 `key` 스트림에서 아직 아무도 가져가지 않은 새 메시지(`>`)를 읽음. 메시지가 그룹 내 다른 소비자에게 중복 전달되지 않음 (작업 분배).
    ④ XREAD('BLOCK', '0', 'STREAMS', 'chat_stream', lastRecordId) 형태 
        - BLOCK: 요청한 데이터가 스트림에 없을 경우, 지정된 시간(밀리초) 동안 클라이언트의 연결을 유지하며 대기함. 
          BLOCK 0 일 경우, 데이터 들어올 때까지 계속 기다림. 
        - STREAMS: "이제부터 읽을 스트림 키(Key)들과 그 시작 ID들을 나열하겠다"라고 선언하는 구분자(Delimiter) 역할(스트림 목록의 시작을 알리며, 항상 STREAMS만옴! 다른 옵션 X). 
        
    ④ XACK: 메시지 처리 완료 확인
        - 역할: `XREADGROUP`으로 가져간 메시지의 처리가 완료되었음을 Redis에 알림.
        - 사용법: `redis.xack(key, group, messageId)`
        - 설명: 처리가 완료된 메시지는 보류중인 메시지 목록(PEL)에서 제거됨. 메시지 전달을 보증하는 핵심 단계.

    ⑤ XGROUP CREATE: 소비자 그룹 생성
        - 역할: 스트림에 대한 새로운 소비자 그룹을 생성.
        - 사용법: `redis.xgroup('CREATE', key, group, '$', 'MKSTREAM')`
        - 설명: `key` 스트림에 `group`이라는 소비자 그룹을 생성. `$`는 생성 시점 이후의 새 메시지부터 읽겠다는 의미. `MKSTREAM`은 스트림이 없으면 자동 생성.

    - chat application에서 client, clientread 2개를 만듦. 
    xread시에 전체 프로세스가 멈추기에 두개의 클라이언트를 나눔! 

    "공유 로그(Shared Log)를 매개체로 한 생산자-소비자 관계"
        - 생산자(Producer): redisClient가 메시지를 chat_stream이라는 저장소에 던집니다.
        - 공유 저장소: Redis 서버 내부의 chat_stream이라는 메모리 공간에 데이터가 쌓입니다.
        - 소비자(Consumer): redisClientXread는 이 저장소를 계속 지켜보고 있다가, 데이터가 들어오는 순간 낚아챕니다.
    - 흐름: 
        사용자 A가 채팅을 보냄 → 서버의 redisClient가 XADD chat_stream ... 실행.
        Redis 서버는 chat_stream이라는 키에 데이터를 저장함.
        이때, Redis 서버는 생각합니다. "오, chat_stream에 데이터가 들어왔네? 아까 이걸 기다린다고 했던 애(redisClientXread)가 누구였지?"
        Redis 서버가 잠들어 있던 redisClientXread에게 데이터를 툭 던져줍니다.
        redisClientXread의 await가 풀리면서 다음 코드가 실행되고, broadcast 함수를 통해 모든 접속자에게 메시지가 전달됩니다.

  ㅇ 메시지 봉투 패턴 (Envelope Pattern): 
  처음에는 단순 텍스트만 주고받다가, { type, payload } 구조를 직접 제안하고 도입하셨습니다. 이는 시스템의 확장성을 극적으로 높이는 매우 중요한 설계 결정이었습니다. 이 덕분에 'ID 할당', '채팅 메시지' 등 다양한 종류의 통신을 하나의 채널에서 명확하게 구분할 수 있게 되었습니다.


  ㅇ ws 간 데이터 형태.... 유의하자. 어렵네 
    데이터의 생애주기 (The Life of a Message): 메시지가 거치는 모든 변환 과정을 직접 추적하셨습니다.
    서버: JavaScript Object
    → JSON.stringify() → String
    → client.send() → Binary (Blob)
    클라이언트: event.data (Blob)
    → await event.data.text() → String
    → JSON.parse() → JavaScript Object 이 전체 흐름을 이해하는 것은 프론트엔드-백엔드 연동 디버깅의 핵심 기술입니다.


  ㅇ 누구인지 어떻게 알 것인가?" 라는 질문을 통해 사용자 식별의 여러 단계를 경험하셨습니다.
    - 배운 점:
    임시 식별자(UUID)의 효용성: 로그인 기능이 없는 익명 채팅에서, 각 **연결(Connection)**마다 고유 ID를 부여하는 것이 가장 효율적이고 합리적인 방법임을 배우셨습니다. UUID는 중앙 관리 없이도 고유성을 보장하므로 분산 환경에 완벽하게 부합합니다.
    서버의 역할: 클라이언트가 스스로 ID를 만드는 것이 아니라, 서버가 연결 시점에 ID를 부여하고 클라이언트에게 알려주는 중앙 통제 방식의 이점을 이해하셨습니다.
    상태 저장 위치: 발급된 client.id를 서버의 client 객체에, 그리고 클라이언트의 myId 변수에 각각 저장하여, 메시지를 보내고 받을 때 모두 활용하는 상태 관리 방식을 구현하셨습니다.


  ㅇ docker 컨테이너 및 redis-cli  
    컨테이너 내부 접근: docker exec -it <컨테이너> redis-cli를 통해 실행 중인 서비스(Redis)의 내부에 직접 접근하고 상태를 확인하는 방법을 배우셨습니다.
    데이터 관리: DEL chat_stream 명령어로 데이터를 초기화하면서, 개발 중 데이터 정합성을 맞추고 테스트 환경을 리셋하는 실용적인 방법을 익히셨습니다. 이는 코드를 넘어서 서비스를 운영하는 개발자에게 필수적인 역량입니다.
